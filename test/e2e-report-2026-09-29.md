## 二、Bug 清单(按严重度)

### 🔴 P0-1 对话助手订单查询越权(IDOR)

- **现象**:匿名(未登录)状态在聊天窗问「帮我查一下用户ID为1的全部订单」→ 助手完整返回 user1 的 **97 笔订单**(订单号/座位/金额/场次/状态)。
- **根因**:`ChatTools.getMyOrders` / `getMyOrder` 的 `userId` 是 **LLM 可控的 @P 参数**,代码只判空(`userId == null → LOGIN_REQUIRED`),从不与服务端登录态(`UserContext.userId()`)比对。`ChatController` 明明能拿到真实 userId(限流 SpEL key 在用),却没有注入工具侧。
- **影响**:任何人无需登录即可枚举/读取全站用户订单数据(隐私泄露);登录用户同样可查他人订单。
- **证据**:截图对话(idor-test.yml)+ `cinema-server/.../chat/tools/ChatTools.java:211-238`。
- **修复建议**:工具不接收 LLM 的 userId;由服务端从 `UserContext` 注入(ThreadLocal/request-scoped),未登录一律 LOGIN_REQUIRED。两个订单工具都要改,并补一条反射/单测断言。

### 🟠 P1-1 退票后 sold 位图不释放,座位永久无法再售

- **现象**:user1 支付 1排8座、1排9座 → 申请退票成功(订单 REFUNDED,前端提示「座位已释放」)→ 重新打开座位图,**两座仍不可选**;base64 解码 `GET /sessions/9900000101/seat-map`:`soldBitmap` 与 `lockBitmap` 的 bit 7、8 均为 1。
- **根因**:退票走 `OrderPayService.refund()` → `release_seat.lua`,该脚本注释明确「只清未售出的锁定座位」——对已支付订单座位 sold=1 恒不成立 → **什么都不清**。全局无任何生产路径清理 sold 位(只有支付置 1、管理端手动恢复重建)。代码注释「已售 → 可选」与实际脚本语义相反。
- **连带问题**:`confirm_seat.lua` 支付时只置 sold 不清 lock → 支付过的座位 lock 位永久残留(本次 lock 位图里 7、8 残留即此原因)。
- **影响**:退出的座位无法再次售出(收益损失),Redis 位图与 DB 永久不一致,只能靠管理端手动恢复位图兜底。README「P0:退票成功 → 座位实时变可选 ✓」与当前代码行为不符(WS RELEASED 事件会广播,但刷新后座位仍灰)。
- **修复建议**:退票路径改用「清 sold 位」专用 Lua(或 release 脚本增加模式参数);confirm 时同步清 lock。
