### 1.2 逐家拆解（功能定位 / 核心能力 / 目标用户 / 差异化优势 / 商业化方式）

#### A. 猫眼（国内电影票务第一）

| 维度 | 内容 |
| --- | --- |
| 功能定位 | 「科技 + 全文娱」服务商：在线娱乐票务 + 娱乐内容服务 + 广告服务 |
| 核心能力 | 在线选座、场次查询、电子取票、退改；**向产业链上游延伸**：宣发、排片、票房预测、数据服务 |

### 1.5 商业化方式：本项目的处理原则

- **本期不做商业化**。项目是课程设计交付物，主用户是评审而非付费用户（依据 E1）。任何「市场份额、ARPU、GMV、转化率」类数字在本项目中**均无数据源**，编造即违反 E7。
- 若未来产品化，可参考的商业化路径（**仅为参考选项，非承诺**）：① 票务服务费（对标 3–5 元/张的公开口径）；② 影院侧 SaaS/白标输出（对标 BookMyShow 的 B2B 路径）；③ 数据服务（对标猫眼）。三者均需真实供给与资质，**不属于本课设范围**。
- 红线：金融/票务属强监管领域，真实支付与资金结算涉及支付资质、发票、退票资金口径与消费者权益保护（如前置全包价、退改阶梯费率），**在课设语境下一律不触碰**（见 §8）。

## 4. 产品方案设计：三个可选方案

> 三个方案解决同一个 R0，但路径与取舍不同。**方案 A 在推荐结论中不作为可选项，而作为必做底座**（理由见 §5.1）。

### 方案 A · 正确性资产化 ——「可被验证的抢票内核」

| 项 | 内容 |
| --- | --- |
| 定位 | 把「Redis 双位图 + Lua 原子锁座 + DB CAS + 延迟关单双保险」从**实现**升级为**可对外出示的工程资产** |
| 核心能力 | ① 一键复现演示脚本（重置 → 补种 → 全链路冒烟 → 压测 → 生成报告）；② 位图对账与自检工具（Redis 位图 vs DB 订单逐座比对）；③ 故障注入与恢复演练（flush 后冷启动重建；超卖不变式回归）；④ 可观测性（锁座成功率、冲突率、延迟队列积压、位图体积告警）；⑤ 稳定性收口（位图 TTL、`maxmemory`、P2-1b 分页、幽灵订单清理） |
| 适用场景 | 验收以「工程严谨性」为主要评分维度；时间紧（≤1.5 周）；不愿承担 LLM 不确定性 |
| 实现成本 | **低–中**（估算 8–10 人天）：无新业务链路，主要是脚本化 + 配置化 + 前后端一处联动改造 |
| 预期收益 | 验收确定性最高（直接命中 G1）；风险最低；产出物（压测报告 + 对账工具）可长期复用 |
| 潜在风险 | 差异化叙事弱 ——「防超卖」是任何课设都能讲的题目；对 G2 贡献有限；若只做 A，项目在竞品坐标系里缺少独特记忆点 |
| 不做会怎样 | RK-03/RK-05/RK-09/RK-11 全部留在盘子里，演示可能现场翻车 |

### 方案 B · 对话助手闭环化 ——「一句话买到票」（推荐）

| 项 | 内容 |
| --- | --- |
| 定位 | 把行动卡片从「跳转到选座页，用户自己再点一遍」升级为「**用户确认即下单**」，写操作仍走既有锁座链路 |
| 核心能力 | ① **Card v2（可确认动作）**：卡片携带 `{sessionId, seatIndexes, seatDesc, 预估金额, 有效期}`，前端渲染二次确认弹窗；② **下单前预检**：确认瞬间重查一次余座，冲突则回传冲突座位并刷新；③ **复用既有护栏**：`@Idempotent` + `@RateLimit` + 15 分钟待支付窗口 + 超时自动释放全部照旧；④ **可解释失败**：40002/42900/40900 三码在对话内给出人话解释 + 替代建议；⑤ **可撤销**：取消仍在既有 `/orders` 页执行，助手不获得写权限；⑥ **成本护栏**：会话级写入上限、LLM 超时与重试上限、用量看板 |
| **护栏设计（关键）** | 助手侧的 `@Tool` **保持只读不变**，`ChatToolsStructureTest` 反射白名单不红；真正的锁座由前端确认后调用**既有** `POST /api/orders/lock`。ADR-0002 的原则（「写入权永远在用户手里」）**不被推翻，只是从「跳页执行」细化为「确认后由既有链路执行」** —— 这是对 ADR 的增补，需要写 ADR-0004 留痕 |
| 适用场景 | 需要一条能被一句话讲清的差异点；能接受 LLM 不确定性；有 2–3 周且 A 的底座已就位 |
| 实现成本 | **中**（估算 10–12 人天）：Card v2 协议扩展 + 前端确认弹窗 + 预检与冲突回传 + 护栏 + 测试；不需要改 Lua、不需要改订单状态机 |
| 预期收益 | **高**：直接命中 G2；对齐 2026 年已被行业验证的赛道（千问 × 大麦）；演示冲击力最强（一句话 → 出票）；与产品原则第 4 条「写入权永远在用户手里」完全兼容 |
| 潜在风险 | RK-02（红线触碰，已有架构化解法）、RK-06（LLM 不可控，已有降级）、RK-07（视图层难测，已有三段式方案）；若预检缺失，可能「建议有座、下单冲突」造成体验落差 |

### 方案 C · 经营决策侧 ——「影院经营大脑」

| 项 | 内容 |
| --- | --- |
| 定位 | 从「卖票系统」延伸到「经营决策系统」：排片建议、上座率/票房预测、动态定价、满场预警、营收对账 |
| 核心能力 | 排片优化模型、需求预测、上座率看板升级、定价策略实验、经营异常告警 |
| 适用场景 | 面向 B 端运营；有多周时间；且**有真实历史数据** |
| 实现成本 | **高**（估算 20+ 人天）：需要数据、特征、模型与实验框架，且前端要新增一套分析界面 |
| 预期收益 | **中**：对真实影院有价值，但对本项目主用户（评审）契合度中等；且数据与结论难以验证 |
| 潜在风险 | **RK-13（新增，未在登记册正式编号）**：无真实用户与订单数据（E7），任何「预测准确率 +30%」类结论都是编造，反而触碰「证据来自实跑」的产品原则第 2 条；范围大，极易蔓延挤占 Must 带 |
| 结论 | **本期不做**，记入后续版本池；触发条件见 §6.4 |

## 5. 推荐方案与理由

### 5.1 推荐结论

> **推荐：以方案 B 为演进主轴，方案 A 为必做底座；方案 C 本期不做，记入后续版本池。**
>
> 落地顺序：**先 A（底座）→ 再 B（MVP）**，不可并行抢资源。

### 5.2 为什么推荐 B（而不是只做 A）

1. **A 解决的是「不丢分」，B 解决的是「拿高分」**。A 是验收的安全网（RK-03/RK-05 直接关掉），但「防超卖」是课设题目的标配动作，不构成记忆点；B 的「一句话买到票」在 2026 年已是行业头部产品的真实能力，具备对外讲述的势能。
2. **B 的技术门槛被高估了**。骨架已就位：8 个只读工具、行动卡片解析（`ReplyCardParser`）、卡片→选座页的路由(`actionCardRoute`)与 preselect 应用纯函数(`computeApplyPreselect`,10 条用例)。B 的本质是**把卡片的目标地址从「选座页」改成「确认弹窗」**，不需要改 Lua、不需要动订单状态机、不需要给助手写权限。
3. **B 不违背产品原则**。原则第 4 条是「写入权永远在用户手里」——B 的每一步写入都需要用户显式确认，比现在的「跳页后用户自己点」更可控。原则第 1 条「正确性 > 功能量」也满足：写入仍走既有链路，防超卖不变式不放松。
4. **A 与 B 不是二选一，是先后关系**。B 的演示价值建立在「演示能稳定复现」之上，而 A 正是这件事；先做 A 约 8–10 人天，是 B 的前置投资。

### 5.3 为什么不选 C

- **数据前提不成立**：`PRODUCT.md` 明确「没有真实用户、真实订单、客户评价、媒体报道或商业数据」。没有数据支撑的「经营大脑」只能产出编造的数字，直接违反产品原则第 2 条。
- **投入产出比最差**：估算 20+ 人天，恰好会吃掉 Q4 假设的 3 周总预算，挤爆 Must 带（RK-04）。
- **不是不做，是时候未到**：见 §6.4 的触发条件。

### 5.4 推荐方案的护栏清单（B 立项的前置条件，缺一不启动）

| # | 护栏 | 验收方式 |
| --- | --- | --- |
| H1 | `ChatTools` 的 `@Tool` 方法**保持只读**，不新增任何写方法；`ChatToolsStructureTest` 反射白名单必须保持全绿 | 单测断言 |
| H2 | 锁座只经既有 `POST /api/orders/lock`，不新增助手专用下单接口 | 接口清单 diff 审计 |
| H3 | 确认卡片必须**二次确认**（弹窗 + 明示场次/座位/金额），不接受一键直下 | Playwright 用例 |
| H4 | 确认瞬间**预检余座**；冲突时回传冲突座位 + 自动给出替代连座建议 | 单测 + E2E |
| H5 | 写路径复用既有 `@Idempotent` + `@RateLimit`；新增会话级写入上限 | 单测 |
| H6 | 新增 **ADR-0004** 记录「确认式下单」对 ADR-0002 的增补，留痕可追溯 | 文档评审 |
| H7 | 助手侧写操作事故数 = **0**（红线，恒定指标，见 §7.5） | 审计日志对账 |

### 6.2 MVP（v1.0）范围声明

**MVP 包含**：
- 单场景闭环：用户用自然语言表达「某片 + 某时段 + N 连座」→ 助手返回可确认卡片 → 用户二次确认 → 走既有锁座 → 出票。
- 三种失败可解释：座位冲突（40002）、限流（42900）、幂等冲突（40900）。
- H1–H7 全部护栏。

**MVP 不包含（明确不做，避免歧义）**：
- 助手直接支付（支付仍在既有 `/payment` 页）。
- 助手退票/改签执行（v1.5 只做**引导卡片**，不执行）。
- 多轮议价、优惠券、会员体系、卖品。
- 任何真实资金流。
- 方案 C 的任何预测/定价能力。

### 6.3 关键状态机（确认式下单，增补而非替换）

```
[用户自然语言]
      ↓
[助手只读工具查询] ──(无结果/需澄清)──> [追问卡片]
      ↓
[Card v2: 建议卡片 {sessionId, seatIndexes, amount, expireAt}]
      ↓
[用户点击确认] ──(H3 二次确认弹窗)──> [取消] → 回到对话
      ↓
[H4 下单前预检: 重查余座]
      ├── 有余座 → [既有 POST /api/orders/lock] ──(H5 幂等+限流)──> [PENDING_PAY]
      │                                                              ↓
      │                                                    [既有 15min 倒计时 / 超时自动释放]
      │                                                              ↓
      └── 冲突   → [回传冲突座位 + 替代连座建议]           [既有 /payment → PAID → 电子票]
```

> 注意：这张图里**没有一个新的状态**。所有状态（PENDING_PAY / PAID / CANCELLED / REFUNDING / REFUNDED）与既有订单状态机完全一致。**MVP 不改状态机，只改「谁触发了锁座」这一跳的入口**。这是本方案成本可控的根本原因。

### 7.2 阶段性目标与验收标准（GWT）

#### 阶段 0 · v0.9 底座（5–7 天）

**目标**：让「一次可复现的演示」与「可验证的正确性证据」成为随时可出示的常态产物，并关掉 RK-05/RK-09。

| 编号 | 验收标准（Given / When / Then） |
| --- | --- |

## 8. 资金与合规红线（前置声明）

- **本期不接入真实支付**，维持 `MockPaymentService` / `MockRefundService`。因此资金类专项检查清单（幂等 + 对账 + 资损监控三件套）**本期不触发**，但**已有基础**：`@Idempotent` 幂等键、`refund_log` 退款日志、订单状态机与卡死补偿任务。
- **一旦未来接入真实支付**，以下为不可砍底线，需单独评审：① 幂等键（业务主键 + 渠道流水号）；② 与支付渠道的日对账与差异留痕；③ 四类资损告警（重复支付、负金额、状态回跳、对账差异）；④ 金额以**分**或 Decimal 存储计算，禁止浮点；⑤ 退款金额与手续费口径明确、支持部分退款、原路退回；⑥ 支付状态机回调 + 主动查询双通道，防状态回跳。
- **票务属强监管领域**：真实经营需相应资质；票务价格展示需符合「前置全包价」的消费者权益要求（参考 FTC junk fees 规则与国内对服务费明示的要求）；退改签需明示阶梯费率与时间窗口。**课设语境下不触碰真实交易。**
- **个人信息**：示例数据一律虚构并脱敏；本项目测试账号为 `user1/user2/admin`（公开种子数据），无真实个人信息。

## 9. 附录

### 9.1 用户故事（MVP 核心）

**US-01 · 一句话找到票并锁座**
> 作为**观影用户**，我想要**用一句话描述「哪部片、什么时间、几个连座」就拿到可直接确认的座位方案**，以便**不用在列表、详情、选座三页之间来回切换**。

- Given 我已登录且目标场次有连座，When 我说「帮我找《X》今晚 8 点左右两连座」，Then 助手返回一个可确认的座位卡片。
- Given 卡片已返回，When 我点击确认并在弹窗中再次确认，Then 座位被锁定并生成 15 分钟待支付订单。
- Given 确认瞬间座位已被他人抢走，When 我二次确认，Then 我收到明确的冲突提示与一组替代连座建议。

**US-02 · 评审看得到正确性证据**
> 作为**课程评审**，我想要**在一次演示里同时看到全链路体验与并发正确性证据**，以便**相信这个系统不是跑通就算，而是真的卖不错**。

- Given 一键脚本执行完毕，When 我查看报告，Then 我看到 27 条 E2E 断言、250 并发 0 超卖、三场景压测的 QPS/P99/错误率，且全部为本次实跑产物。

**US-03 · 助手不会背着我下单**
> 作为**观影用户**，我想要**确认助手永远不会未经我确认就锁座或付款**，以便**放心使用对话入口**。

- Given 一轮对话中我从未点击确认，When 审计日志被检查，Then 写操作计数为 0。
