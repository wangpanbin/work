# 影院抢票选座系统：下一轮小迭代计划

> 迭代主题：**Seat Watch——指定座位释放提醒**  
> 调研日期：2026-10-19  
> 项目范围：`F:\test\work`；本计划基于当前仓库文档与代码结构制定，不包含直接修改现有代码。

## 一、结论先行

**建议下一轮只做一件事：让用户关注暂时被占用的座位，在座位释放时收到页面内提醒。** 同时修复一个与该功能直接相关的实时状态同步缺口。

项目现在已经有选片、场次、实时选座、锁座、支付、取消/退票、电子票、管理看板和只读对话订票助手。继续堆“影评、会员、优惠券、更多 AI 聊天”等宽泛功能，开发范围会迅速膨胀，也很难超过大型票务平台的内容、用户和交易规模。下一步更合适的策略，是把现有的 Redis + Lua + WebSocket 优势转化成用户能直接感知的体验：**不用反复手动刷新座位图，也能及时知道自己关注的座位刚刚释放。**

建议把这一轮拆成两个紧密相关的小交付：

1. **先修复实时释放事件的前端状态同步**，确保退票后释放的座位不再残留“已售”显示。
2. **再实现指定座位释放提醒**，复用现有 WebSocket `RELEASED` 事件，不增加新的后端服务、数据库表或 AI 依赖。

## 二、项目现状判断

根据根目录 `README.md`、`cinema-web/PRODUCT.md` 和当前代码：

- 核心交易流程已完成，系统主要技术价值是高并发防超卖、实时座位状态同步、支付与关单竞态保护。
- `SeatSelect.vue` 已连接 `/ws/seat/{sessionId}`，处理 `LOCKED`、`RELEASED`、`SOLD` 事件，并有连接状态提示和手动刷新入口。
- `SeatEventPublisher` 已有 `publishReleased(sessionId, seats)`；主动取消、超时关单和退票流程都会发布释放事件。
- 对话式订票助手已经能够查场次和座位、推荐连座，并用行动卡片跳转既有选座流程。因此本轮没有必要再做一个泛化的聊天入口。
- 项目已包含前端 reducer 的纯函数测试接缝，适合先补状态机测试，再扩展 UI；无需先引入新的测试框架。

### 发现的一个相邻缺口

当前 `cinema-server` 的 `OrderPayService.refund()` 会调用退款专用的 `refundSeats(...)`，清除 Redis 中已售/锁定状态，随后广播 `RELEASED`。但前端 `cinema-web/src/stores/seatEventReducer.ts` 的 `computeApplyEvent()` 处理 `RELEASED` 时目前只把 `newLockBits[s]` 置为 `0`，没有同步清除 `newSoldBits[s]`。

**结果：其他仍停留在选座页的用户可能继续看到该座位为“已售”，直到手动刷新或重新进入页面。** 这会削弱实时座位系统的可信度，也会直接影响释放提醒的正确性，应作为该迭代的第一项修复。修复时需为 `RELEASED` 的位图变化补充回归测试，并留意并发锁座事件紧随释放事件到达的情况；提醒文案应表达“刚刚释放，可能被其他用户再次锁定”，而不是承诺该座位仍可购买。

## 四、功能设计：Seat Watch 指定座位释放提醒

### 4.1 用户场景

用户进入某场次的座位图，发现自己想要的座位暂时被他人锁定，或座位已经售出。用户可以开启“座位提醒模式”，点击最多 8 个不可选座位进行关注。当这些座位收到 `RELEASED` 事件且本地状态确认已恢复可选时，系统在当前选座页面发出提示，用户自行决定是否选中并提交锁座。

### 4.2 用户流程

1. 用户进入现有选座页，页面先完成座位图加载并连接 WebSocket。
2. 用户点击“关注座位释放”按钮进入提醒模式，页面显示简短提示：点击被占用的座位即可关注，最多 8 个。
3. 用户点击 `LOCKED_OTHER` 或 `SOLD` 座位，切换该座位的关注状态；被关注座位显示铃铛/描边标识，并提供 `aria-label` 或 title 文本说明。
4. 收到 `RELEASED` 事件时，先应用座位状态更新，再筛选被关注且状态已恢复可选的座位。
5. 命中时合并为一条提示，例如“第 5 排 6 座刚刚释放，试试选座”。提醒后自动取消该座位的一次性关注，避免反复打扰。
6. 用户仍需手动选座并点击原有确认按钮。系统**不自动选座、不自动锁座、不自动下单**。

### 4.3 范围约束

- 本轮只实现**当前场次、当前浏览器页面存活期间**的提醒。用户关闭页面、切换离开当前场次或断开 WebSocket 后，不承诺继续提醒。
- 关注状态只存在前端内存，不写数据库、不跨设备同步。刷新页面后清空。
- 优先复用现有 `RELEASED` 事件，不增加 REST API、数据库迁移、消息中间件或外部推送。
- `LOCKED`、`SOLD` 等事件继续按现有机制更新座位；新功能只观察事件，不触碰锁座、支付、退票等写路径。
- 释放提醒是机会提示，不是座位预留。座位可能被其他用户几乎同时锁定，实际能否购买仍以原有后端锁座接口结果为准。

## 五、实施拆解

### Task 1 — 修复 `RELEASED` 状态同步

**涉及位置**

- `cinema-web/src/stores/seatEventReducer.ts`
- 对应 reducer 单测（按仓库现有测试目录与命名扩展）

**工作内容**

- 补充 `RELEASED` 事件的状态转移测试：包括“仅被锁定的座位释放”和“已售座位退票释放”两种初始位图。
- 依据 `RELEASED` 的后端语义同步更新 lock/sold 位；验证座位状态从 `LOCKED_OTHER` / `SOLD` 回到 `AVAILABLE`。
- 验证释放事件不会把当前其他座位的 selected 集合清空，也不会意外移除其他仍有效的选中座位。
- 检查 `LOCKED`/`SOLD` 紧随释放事件到达时，座位最终状态仍能被后续事件正确覆盖。若当前纯增量更新无法稳定覆盖竞态，优先在现有事件处理层增加小范围的权威状态协调，不要扩展成全新实时架构。

**验收标准**

- 单测覆盖释放前后 lock/sold 位的变化。
- 退票后仍打开的另一个选座页面能把被释放座位显示为可选，不依赖用户点击手动刷新。

### Task 2 — 加入提醒模式和关注状态

**涉及位置**

- `cinema-web/src/views/SeatSelect.vue`
- `cinema-web/src/components/SeatItem.vue`
- `cinema-web/src/i18n/locales/zh-CN.ts`
- `cinema-web/src/i18n/locales/en-US.ts`

**工作内容**

- 在座位图上方或图例附近加入“关注座位释放”开关按钮和一句简短使用说明。
- 提醒模式打开时，点击不可选座位的行为改为添加/取消关注；普通模式下保持现有提示行为不变。
- 每场最多关注 8 个座位；达到上限时显示明确提示。
- 通过铃铛图标/描边等非纯颜色信号区分关注座位，并保持座位状态的可访问性标签。
- 新增文案同时补中英文翻译，不硬编码单语言字符串。

**验收标准**

- 普通选座模式行为不变。
- 关注可以添加、取消，超过上限有提示。
- 键盘/屏幕阅读器的状态标签能区分“关注中”，不能只依赖颜色。

### Task 3 — 接通释放提醒

**涉及位置**

- `cinema-web/src/views/SeatSelect.vue` 的 WebSocket 事件回调
- 可选：将关注命中判断抽为纯函数，方便 Vitest 覆盖

**工作内容**

- 在应用 `RELEASED` 事件后检查被关注座位；只对状态已恢复可选的关注座位发出提醒。
- 多个关注座位在同一事件中释放时合并为一条通知，避免连发多个 toast。
- 提醒后取消对应的一次性关注；若座位又被其他用户锁定，仍以实时座位状态显示，不把提示当作锁定保证。
- WebSocket 断开时明确显示“实时提醒暂不可用”，沿用已有连接状态栏，不另建连接或轮询器。

**验收标准**

- 只有被关注座位的 `RELEASED` 事件会触发提醒。
- 未关注的释放、`LOCKED` 和 `SOLD` 事件都不会误触发提醒。
- 提醒过程中没有任何自动锁座、建单、支付或退票请求。

### Task 4 — 回归测试与演示验证

**测试场景**

1. **超时/取消释放**：账号 A 关注账号 B 已锁定的座位；B 取消订单或待支付订单超时关闭；A 收到提示，座位恢复可选。
2. **退票释放**：已支付订单退票后，仍在线的 A 收到关注座位释放提醒，座位状态正确从已售变为可选。
3. **抢座竞态**：释放后另一用户迅速重新锁座；A 可能看到“刚刚释放”的提示，但不能绕过服务端校验，原有锁座冲突处理必须仍然有效。
4. **关闭/断开**：关闭页面或 WebSocket 断开后，不声称还能收到实时提醒。
5. **原功能回归**：普通点击选座、对话助手行动卡片预选、锁座、支付、取消、退票及 250 并发抢座防超卖测试保持通过。

**建议执行的门禁**

- 后端：`cd F:\test\work\cinema-server && mvn test`
- 前端：`cd F:\test\work\cinema-web && pnpm test`
- 前端构建：`pnpm build`
- 类型检查：`pnpm type-check`
- 最后使用真实浏览器跑上述双账号场景，保留一组前后对比截图用于答辩演示。

项目文档已明确：测试用例数量以实跑为准；`pnpm build` 与 `pnpm type-check` 检查范围不同，两者都应执行。

## 七、成功标准

- 用户能在几次点击内关注想等的座位，并清楚理解提醒范围。
- 被关注座位释放后，当前在线页面可以及时提示；未关注座位不会制造额外打扰。
- 释放提醒不会自动改变用户选择、不会替用户锁座，既有“写入权在用户手中”的设计原则保持不变。
- 退票释放的座位状态能实时回到可选，避免必须手动刷新。
- 后端锁座与支付核心路径无新增写入口，防超卖回归测试继续通过。
- 双账号演示能完整展示“关注—释放—通知—用户确认选座”的差异化闭环。

## 八、暂缓的其他创意

- **个性化观影推荐**：竞品已有较成熟的内容、会员及推荐生态；本项目当前电影数据量和真实用户数据不足以做出可信推荐。
- **更复杂的 AI 代订票**：大麦等产品已有 AI 购票与选座操作先例；而且本项目已明确把对话助手限定为只读建议，不应为了少点一次按钮而绕开锁座安全边界。
- **会员积分、优惠券、社交影评**：需要交易、内容审核和运营规则，远超“小迭代”范围。
- **全局候补/系统推送**：涉及页面关闭后的任务生命周期、用户身份关联、通知通道和权限管理，适合在“当前页面内提醒”验证有价值后再决定是否扩展。
