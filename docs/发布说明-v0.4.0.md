# 发布说明 — v0.4.0

- 日期:2026-10-25
- 版本:`cinema-server` 0.3.0 → **0.4.0**;`cinema-web` 0.3.0 → **0.4.0**
- 主题:**补齐欠账 + 修一个超卖级缺陷** —— 把战略计划里从未落地的 5 个功能项做掉,
  同时堵上二次双轴评审发现的「位图重建会抹掉并发锁座」这道超卖窗口
- 数据库:**新增一张表**(`sql/08_chat_assistant_log.sql`);不涉及既有表的结构变更

## 一句话

**这一版把「已知但没做」清干净了**:浏览器回归套件从 2026-08-31 躺了两个月到现在,
重新跑起来发现 6 处断言过期(没有一处是产品缺陷,已逐条核对根因);
战略计划里挂了两轮的 5 个功能项(演示脚本 / 写审计 / 引导卡 / 浏览器回归 / 用量看板)全部落地;
**而二次双轴评审在位图重建里挖出一道超卖窗口** —— 那道窗口比 v0.3.0 修掉的那个更窄,
但同样致命。

## 一、修了什么(真缺陷)

### 1. ⚠️ 位图重建会抹掉「快照之后新产生的锁座」——超卖级

**之前**:v0.3.0 把位图重建改成了「临时 key + 原子 RENAME」,看着比「先删后建」安全 ——
它挡住了**失败**那道口(重建失败 = 正式位图一个位都不动)。但漏了**并发**那道口:

```
SeatBitmapRebuilder 查库 → 拼快照 → 进 Lua 脚本 → RENAME 覆盖正式位图
                       ↑                                    ↑
                       └── 一次网络往返 ──┘
```

那段时间里任何一次锁座都会把位写进正式位图,而这份锁**不在快照里**
(订单行可能还没提交)→ RENAME 覆盖后被抹掉 → 座位回落为「可选」
→ 另一人可以锁到同一座位 → 同一座位两张待支付单 = **超卖**。

冷启动路径(`ensureBitmaps` → `OrderLockService.lockSeats`)尤其危险:
位图刚被清掉,所有人同时抢座,窗口内的每一把锁都会被抹掉。

**现在**:`merge_seat_bitmap.lua` —— **合并结果 = 正式位图 OR DB 快照**(只加不减),
且合并与换名在**同一个脚本**里原子完成。脚本执行期间不会有别的命令插进来,
「快照之后新产生的锁」一定已经落在正式位图里,OR 之后被完整保留。

> **语义变化**:座位只可能变不可选,绝不可能变可选(宁可锁死也不误放)。
> **代价(有意为之)**:在线重建不再清空位图,位图也不再自动收缩 ——
> 泄漏位与体积收缩交给离线工具 `tools/reconcile_seat_bitmap.py --fix`。
>
> `SeatLuaServiceBitmapRoundTripTest` 新增了一条**回归用例**:
> 合并不得抹掉快照之后新产生的锁 —— 旧实现下这条断言会红。

### 2. `refund_seat.lua` 的注释与实现不符(方向是对的,注释是错的)

注释写着「标记在『确实执行了释放』时写入」,实现却是**无条件写**。复核后确认:
**无条件写才是对的** —— 条件写会把这个脚本专门要堵的超卖窗口重新打开
(第一次调用没释放到座位 → 标记缺失 → 补偿任务第二次再调 → 那批座位若已被他人买走
→ 第二次清位把别人已付款的座位清成可选)。已把注释改成写清「为什么无条件」。

### 3. 两个视图的错误态**没有样式**

`AdminHome.vue` / `LiveDashboard.vue` 用了自造的 `welcome-error` / `live-error` 类名,
全仓**没有对应的 CSS 规则** —— 错误态是裸 div(另外三个视图用的是 `main.css` 里
共享的 `.load-error`)。已改成共用同一份。

### 4. `docs/实现方案.md` 有一处**假陈述**

原文说被删的 `recover_seat_bitmap.lua`「既无生产调用方」——
假的,`SeatBitmapGuard.ensureBitmaps` → `OrderLockService.lockSeats:84` 就是它的生产调用方。
已改,并把 §4 尾段重写为新的「合并」语义。

### 5. 提醒模式下的座位被误报为「不可用」(无障碍缺陷)

`SeatItem.vue` 的 `aria-disabled` 直接绑 `unavailable`(已售 / 他人锁定),
但**提醒模式下这两个状态是可以点的**(点了就是切换关注)。
`focusable` 早就考虑了 `watchable`,`aria-disabled` 漏了 —— 于是读屏用户被告知
「这个按钮不可用」,而它其实能用。

这条是**浏览器回归套件 S17 撞出来的**:Playwright 看到 `aria-disabled="true"`
就拒绝点击(它把 `aria-disabled` 当作「不可交互」)。
已改成 `unavailable && !watchable` —— 与 `focusable` 用同一套判据。

### 6. 两个压测脚本的用户名带时间戳 → 把注册限流额度吃光

`test/concurrency_strict.py` 与 `test/load_test.py` 每次跑都用**时间戳后缀**造用户名,
于是每跑一轮就注册一批新用户。注册端点按 IP 限流 **120 次/小时**
(`AuthController#register`,v0.3.0 加的安全基线)—— 一轮演示要注册 50 + 100 = 150 个,
**单轮就超额度**,第二轮必然 42900「注册过于频繁」;用户没建出来 → 紧接着的登录拿不到 token
→ 报成一个莫名其妙的 `TypeError: 'NoneType' object is not subscriptable`。

已改:**两个脚本共用同一个 50 人池**(`tuser0..tuser49`,用户名稳定不再带时间戳)——
冷启动只注册一次(50 ≤ 120),之后每次跑直接登录复用;
两个脚本的池子一致,压测留下的订单也能被 `demo_run.py --reset` 一并清掉。
登录失败时脚本现在会直接说「多半是注册被限流」,而不是抛 TypeError。

> 另一个连带发现:`test/concurrency_strict.py` 硬编码 `SID = 1`,而
> `sql/05_refresh_sessions_for_demo.sql` 会按日期重建场次(新 ID 形如 10102503)——
> 老 ID 不复存在 → 250 个锁座请求全部失败 → 脚本判「目标座位没被抢」→ **假超卖告警**。
> 已改成走公开 API 动态挑一个「在售 + 未开演 + 有两个可选座位」的场次。
>
> 还有一条更隐蔽的:它原本断言「**该场次**待支付单 ≤ 1」—— 同一场次里可能有
> **别的测试**(浏览器回归 S16/S17 就在同一个场次上建单)留下的待支付单,算进去就判超卖。
> 已改成「**占着目标座位**的待支付**订单数** ≤ 1」——
> 而且必须 `COUNT(DISTINCT o.id)`:一张单占两个座位就是两行,`COUNT(*)` 会把
> 「1 张单占 2 个座」数成 2 张单,同样是假超卖。

### 7. ⚠️ 一键下单确认卡在真实对话里**根本出不来** —— 提示词与解析器的契约互相矛盾

**之前**:`CinemaAssistant` 的系统提示词写着:

> 出 `ORDER_PROPOSAL` 卡**之前必须先调 `findContiguousSeats`** 拿到真实座位索引填进
> `seatIndexes`;拿不到就不出这张卡。

而解析器(`ReplyCardParser`)、服务端(`OrderProposalService`)、前端(`buildRepickRequest`)
**全都把 `seatIndexes` 当成可选** —— ADR-0004 的决策 D8 早就定了「座位最终由服务端重读实时位图决定」。

于是模型陷入死循环:要出卡 → 得先有座位 → 得先定场次 → 一晚有多个候选场次时
它就反问「你打算看哪一场、坐几个人?」→ **永远走不到下单卡**。
实测三次真实调用,返回的全是 markdown 表格 + 反问,`cards=0`。

**影响**:AC-20 那条浏览器验收(对话浮窗 → 下单卡 → 确认下单)长期停在 **SKIP** ——
不是「没验」,是「压根验不了」:真实 LLM 出不出卡取决于模型当天怎么发挥。

**现在**:
- 提示词改成「`seatIndexes` **可选**,通常直接省略(服务端会重读实时位图自己挑连座)」
- 新增「**不要反问**」:用户已表达下单意图时,场次自己挑(有余座优先)、张数按措辞推断
- 张数缺省 **2 张**(用户完全没提时),不再为这个反问
- 加 `CinemaAssistantPromptTest` 把「提示词 ↔ 解析器契约」变成会红的断言
  (卡型集合与 `ActionCardVO` 一致 · `seatIndexes` 必须声明为可选且不得出现「必须先调」·
  「不要反问」与「默认给 2 张」必须在)。**负向验证已做过**:把提示词还原成修复前的版本,
  前两条会红。

### 8. 浏览器回归 S22 的判据与**界面语言**耦合

S19(中英双语切换)把界面切成了英文,而 S22 用**中文**正则「订单号」去找订单号 ——
订单其实早就建成了,场景却报「点了确认下单但没看到订单号」。
判据改成**服务端事实**(user1 的订单列表里冒出新订单)+ **语言无关的选择器**(`.pending-card`)。
顺带给套件加了 `--only S22`(只跑指定场景,调试单场景用)。

## 六、升级方式

1. 拉代码。**需要跑一次新迁移**:`sql/08_chat_assistant_log.sql`。
   不跑它 → 写审计被 try/catch 吞掉(不影响下单),但管理端「助手用量」看板是空的。
2. 建议先跑一遍只读探针:`python tools/check_redis_safety.py`。
3. `mvn spring-boot:run` 启动后端、`pnpm dev` 启动前端。
4. **生产部署**必须设的环境变量(默认值只适合开发):

   ```bash
   export SPRING_PROFILES_ACTIVE=prod
   export JWT_SECRET="<至少 32 字节的随机串>"
   export CORS_ALLOWED_ORIGINS="https://your-domain.example"
   export CINEMA_SEED_ADMIN_ENABLED=false
   # 估算成本的单价(美分 USD / 每百万 token)—— 2026-10-25 DeepSeek flash 非高峰价
   export CINEMA_CHAT_PROMPT_PRICE_PER_MILLION_CENTS=15
   export CINEMA_CHAT_COMPLETION_PRICE_PER_MILLION_CENTS=60
   ```

   不设 `JWT_SECRET` 就等于没换密钥;不切 profile 就会自动播种 `admin/123456`。
5. 演示前跑 `sql/05_refresh_sessions_for_demo.sql` 补场次(幂等)。
6. 验收前跑一遍四套闸门:`python tools/run_all_gates.py`。
7. 想一次跑完全流程:`python tools/demo_run.py`。
