# 2. 行动卡片不执行写操作

- 状态:已接受
- 日期:2026-09-21
- 决策者:项目作者
- 相关:`docs/superpowers/specs/2026-09-21-chat-assistant-design.md`、`CONTEXT.md`(行动卡片)

## 背景

对话助手需要在"能帮用户把票订下来"这件事上有实际价值。最激进的做法是让模型直接调用锁座、下单、支付。次激进的做法是助手返回一个结构化建议,用户点击后由服务端代为提交。

系统的相关约束(均有代码级证据):

1. **`OrderLockService.lockSeats` 流程中包含 `closeIfUnpaid`** —— 锁座前会关闭该用户在该场次**既有的**待支付订单。
2. **`OrderController.lock` 的 `@Idempotent` 键为** `userId + ':' + sessionId + ':' + seatIndexes`,即**包含精确座位组合**。P0 spec §3.3 明确要求"锁座幂等键必须钉住精确座位组合",这是已通过的验收门禁。
3. **锁座冲突是整单失败语义**(`lock_seat.lua` 任一冲突则全部失败),机器遇到冲突的自然反应是换座重试,会与真实用户的抢票行为互相踩踏。
4. 锁座是抢票链路的**唯一写入入口**,整个系统围绕它做了 Redis Bitmap + Lua + CAS + 延迟队列 + 补偿任务的多重保护。

## 决策

助手的输出是**行动卡片** —— 一个**建议**,不是执行。卡片只携带 `{sessionId, seatIndexes, seatDesc, totalAmount}` 等展示与跳转所需的信息,**不携带任何可直接提交的载荷**。真正的锁座只能由用户在前端既有流程中确认后,经 `POST /orders/lock` 发生。

助手**不注册任何写工具**:不存在 `lockSeats` / `pay` / `cancel` / `refund` 之类的 `@Tool` 方法。

## 理由

1. **副作用的可见性。** 证据 1 的 `closeIfUnpaid` 会**静默**释放用户手选的、正在支付倒计时中的座位。这种副作用只有在用户主动确认时才是可接受的。让模型触发它,用户既看不到也拦不住。
2. **不绕过已验收的幂等门禁。** 若助手合成一次锁座调用,它自带一个模型生成的座位列表 —— 等于用**新的幂等键**绕过了 P0 spec 那条"必须钉住精确座位组合"的门禁。模型重试或幻觉即产生第二把钥匙。
3. **冲突语义不适合机器自主重试。** 机器换座重试在抢票场景下是有害的:它会放大对 Redis bitmap 的写入压力,并干扰真实抢票用户的成功率。
4. **"建议"与"执行"的分离让整件事可测。** 卡片是纯数据,可以被精确断言;而"模型自主决定调了什么"无法回归。

## 被否决的替代方案

- **全自动代办(模型直接锁座/下单)**:把抢票链路最脆弱的并发命门交给一个会幻觉、会重试、会超时重发的组件。一次幻觉锁座就污染 Redis 位图并踢掉用户已选座位。
- **服务端代提交(端点 `POST /api/chat/actions/{id}`)**:看似比全自动安全,但它**同样绕过**了证据 1 的可见性与证据 2 的幂等键门禁 —— 只是把触发者从模型换成了服务端。且 `/api/chat/**` 不挂 `@RateLimit`/`@Idempotent`,代提交会引入一条不受既有保护覆盖的锁座路径。

## 后果

- 前端需要把卡片接线到既有 `/seat/:sessionId` 流程(通过 `preselect` query 预选座位),这是本功能**唯一**触碰选座交互的地方,不改动 `lockSeats()` 调用路径。
- 验收门禁新增一条硬性断言:纯聊天之后,用 `redis-cli` 确认 `cinema:session:*:lock` 与 `cinema:user:pending:*` **无任何变化**。
- 可用反射断言 `ChatTools` 上的 `@Tool` 方法白名单,确保没有写方法被误加。
- 代价:助手不能替用户"一步到位"完成下单。这是有意接受的 —— 在抢票系统里,用户对锁座的确认权比一步到位的便利更重要。

## 备注

`CONTEXT.md` 中「行动卡片」词条已明确规定"**是建议,不是执行**",本 ADR 是该词条的决策依据。
