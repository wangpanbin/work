# 3. 对话助手不引入 RAG

- 状态:已接受
- 日期:2026-09-21
- 决策者:项目作者
- 相关:`docs/superpowers/specs/2026-09-21-chat-assistant-design.md`

## 背景

"给系统加一个 LLM 助手"的默认技术反射往往是接一套 RAG:文档切分、Embedding 模型、向量库、召回重排。

本项目要做的事情是**查影片、查场次、查余座、查订单、建议座位**。需要被检索的对象是:

- MySQL 里的结构化行(`movie` / `session` / `order` / `order_item`);
- Redis 里的两张实时位图(`cinema:session:{sid}:lock` / `:sold`)。

这些数据的权威来源是确定性的、实时的、结构化的。

## 决策

**不引入 RAG,不引入 Embedding 模型,不引入向量库。**

助手获取事实的唯一途径是**调用只读工具**,工具直接查 MySQL / Redis 并返回已经算好的结论(如"可选 42 座、第 5 排有 2 连座"),而不是让模型去做语义检索。

少数静态长文(影院地址、退改规则)用**固定 prompt 注入或 YAML 配置**承载。

## 理由

1. **向量相似度解决不了这里的任何问题。** "今晚 8 点还有座吗"是一个**带实时状态的结构化过滤**问题。向量检索会返回一批"语义相似"的场次,但无法回答"其中一个具体场次此刻第 5 排第 4 座是否可锁" —— 那是 `GETBIT` 的职责。
2. **会引入第四个存储。** 系统当前只有 MySQL + Redis(+ 进程内)。向量库(无论是独立的还是 Redis 的向量模块)意味着新的运维对象、新的数据一致性面、新的答辩解释成本。
3. **RAG 引入的是陈旧性风险。** 索引是快照,而座位位图每秒都在变。一个基于索引回答"有座"的助手,在抢票场景下会直接误导用户,比答不上来更糟。
4. **"为什么不用 RAG"比"我用了 RAG"更能体现边界意识。** 这个项目里,不用 RAG 是一个有依据的工程判断,而不是能力缺失。

## 被否决的替代方案

- **全量 RAG(向量库 + Embedding)**:见上,与实时结构化数据不匹配。
- **轻量语义检索(仅对影片简介做 Embedding)**:唯一勉强成立的场景是"找一部像《流浪地球》的科幻片"。但项目已有的 `MovieService.search` 支持 `keyword` / `genre` / `region` 结构化筛选(MySQL LIKE),足以覆盖课程设计的检索需求,不值得为它引入 Embedding 模型与新的依赖复杂度。

## 后果

- 无需 Embedding 模型、无需向量库依赖、无需文档切分管道。
- 助手的"知识"完全等价于工具能查到的东西 —— 这让"模型说错"的可能性被压缩到**措辞**层面,而**事实**层面由工具保证。这也是 spec 中"卡片只由工具结果构造,不由模型自由生成"这条约束的基础。
- 若将来真的需要文档问答(如影院 FAQ 长文),届时应作为**独立决策**重新评估,而不是顺带塞进本功能。
