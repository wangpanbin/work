# 4. 对话助手的下单提案(局部修订 ADR-0002)

- 状态:已接受
- 日期:2026-10-19
- 决策者:项目作者
- 相关:`docs/adr/0002-action-cards-do-not-execute-writes.md`、`docs/superpowers/specs/2026-10-19-chat-one-click-order-design.md`、`CONTEXT.md`(下单提案 / 行动卡片)

## 背景

ADR-0002 定了 chat 助手「只读不写」的边界,当时的目标是"在抢票系统里,用户对锁座的确认权比一步到位的便利更重要"。那条决策在当时是对的。

但它同时留了一个缺口:**助手已经能算出「哪几个座位连着、价格多少」,却只能把用户扔回选座页,让他自己再点一次「确认选座」**。用户已经在对话里把意图说清楚了("帮我订明天晚上那场《X》的 2 张连座"),却又被要求用鼠标在座位图上重新做一遍选择。

本轮需求是"**一键对话就能下单**"。这必然要求推翻 ADR-0002 的一部分。本 ADR 的任务是:在**推翻面最小**的前提下把这件事做成,而不是把只读边界整体拆掉。

## 决策

助手可以输出一种新的行动卡片 **`ORDER_PROPOSAL`**,它在对话内**执行一次锁座**(建待支付订单)。

关键设计:**执行权不在模型手里,在用户的一次点击手里;执行用的数据不在模型手里,在服务端快照里。**

1. **模型只负责"备单"**。它输出一张 `ORDER_PROPOSAL` 卡,内容是场次 + 张数 + 座位建议。
2. **服务端装配器**(`OrderProposalAssembler`)拿到这张卡后,**重读实时位图**逐个复核模型给的座位:
   在范围内?当前可选?同行连座?任一不满足就**由服务端重找一组**。价格**一律取 session 表**,模型给的报价直接丢弃。
3. 复核通过才生成一份**服务端提案快照**(`OrderProposal`):userId + sessionId + 座位索引 + 单价 + 总额 + 过期时刻 + 同场次存量待支付单号,存 Redis,默认 TTL 90 秒。
4. 卡片上多一个 `proposalId` —— 它是**服务端快照的引用**,不是载荷。确认端点只凭这个 ID 去 Redis 取快照,**不接受任何客户端传入的座位**。
5. 用户点「确认下单」→ `POST /api/chat/orders/{proposalId}/confirm` → 提案**读出即删** → 复用 `OrderLockService.lockSeats` 锁座 → 订单进入待支付 → 聊天内追加「待支付卡」。
6. **付款仍在支付页由用户自己完成**。助手不代付。

## 逐条回应 ADR-0002 的三条证据

ADR-0002 反对"服务端代提交"时给了四条理由,逐条交代:

**证据 1 —— 锁座会静默取消用户已有的待支付订单。**
→ **部分采纳,已消解**。提案阶段就查该用户该场次的存量待支付单,把订单号写进提案;确认卡上**显式列出**"确认后将取消你当前的待支付单 XXX"。副作用从"静默"变成"知情",且发生在用户点击之前。`OrderLockService.findUserPendingOrder` 由 private 提为 public,提案阶段与锁座阶段复用**同一个查询**,口径不会分叉。

**证据 2 —— 模型重试或幻觉即产生第二把幂等钥匙。**
→ **采纳,已消解**。幂等键是 `proposalId`,不是 `userId:sessionId:seatIndexes`。座位列表**从不进入**幂等键,也从不被模型直接提交 —— 它只作为"提示",且要过服务端三重校验。模型幻觉产生不了一把新钥匙,因为钥匙的来源是服务端自己发的一次性 UUID。

**证据 3 —— 冲突语义是整单失败,不适合机器自主重试。**
→ **完全采纳,未变**。确认失败(40002)时助手**不自动换座**,只告知"这几个座位刚被抢走了"并给一个「重新找一组」按钮 —— 重试的决定权在用户,动作也由用户点出来。机器一次都不会自己去抢座。

**证据 4 —— 锁座是抢票链路的唯一写入入口,整条链路有多重保护。**
→ **完全采纳,未变**。确认端点内部直接调 `OrderLockService.lockSeats`,Redis Bitmap + Lua CAS + 延迟关单 + 补偿释放那一整套保护原样生效。`POST /orders/lock` 与既有抢票链路**一行未改**。

## 明确不变的东西

- **助手不注册任何写工具**。`ChatTools` 仍是 8 个只读 `@Tool`,`ChatToolsStructureTest` 的四条断言**一字未改**。
- **卡片不携带可直接提交的写载荷**。`proposalId` 是快照引用,不是座位/金额本身。
- **付款留在用户手里**。助手不代付、不接真实支付。
- **不做机器自动换座重试**。
- **既有抢票链路零改动**。`POST /orders/lock` 及其 `@Idempotent` / `@RateLimit` 一行未动。
- **`/api/chat/message` 仍然公开可匿名**。只有新加的 `/api/chat/orders/**` 需要登录。

## 后果

- chat 模块第一次有了写路径,必须自带门禁:`/api/chat/orders/**` 已加入 `AuthRequiredInterceptor` 覆盖路径(未登录 → 40101);两个端点各自挂 `@Idempotent` + `@RateLimit`。
- 新增**回滚闸门** `cinema.chat.order-enabled`(默认 true)。关掉它,装配器不建任何提案、两个端点拒服务 —— **不发版即可让整条写路径失效**。
- `CONTEXT.md` 新增「下单提案」词条,并修订「行动卡片」词条。
- 提案 TTL(默认 90s)与订单支付窗口(15 分钟)是两个独立概念:前者是"方案有效期",后者是"座位占用时长"。

## 被否决的替代方案

- **给 `ChatTools` 加第 9 个 `@Tool`(让模型自己调 `prepareOrderProposal`建提案)**:更贴合 LangChain4j 的原生工具编排,但会让 `ChatToolsStructureTest` 的"数量==8"和"名字集合==白名单"两条断言必须改,ADR-0002 的"助手不注册写工具"被字面推翻。**后处理装配层能达到同样效果且改动面更小**。
- **前端拿快照后直接调既有 `POST /orders/lock`**:门禁天然齐全、改动最少,但座位列表变成客户端回传,提案的"一次性快照"语义消失,幂等键退回"用户+场次+座位"维度。**与"服务端按快照执行"直接冲突**。
- **在既有 `/orders/lock` 上加可选 `proposalId` 参数**:一条链路,但侵入全站下单写入口,风险外溢到每一个下单用户。**违反"既有抢票链路零改动"**。
- **服务端代付 / 全自动锁座**:ADR-0002 当初已否决,本轮也不采纳 —— 推翻面会大到失去"可回滚、可解释"这两条底线。
