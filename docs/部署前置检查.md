# 部署前置检查清单

> 面向「把这套东西真跑起来给别人看 / 放到服务器上」的场景。
> 每一项都写清楚了**为什么**要查 —— 只写「照做」不写「不做会怎样」的清单，
> 过两周就没人知道哪一项能跳。
>
> 检查项分三类：
> - **阻断项** —— 不改就会出事（超卖 / 进程起不来 / 数据被写坏）。
> - **必填项** —— 不填就跑不出预期功能。
> - **知会项** —— 可以先这样，回头再优化。

配套的自动化探针：`tools/check_redis_safety.py`（只读，不改配置）。

# Redis(只读探针; FAIL 项必须先改)

## 1. Redis（阻断项最多的一节）

Redis 在这套系统里不是「缓存」，是**防超卖的唯一防线**。
锁座位、卖座位、退票放座位，三条路径都靠 Redis 位图 + Lua 脚本。

### 1.1 `maxmemory-policy` 必须是 `noeviction` —— 阻断

```bash
redis-cli CONFIG GET maxmemory-policy
```

**为什么**：只要策略允许驱逐，Redis 在内存触顶时就会**踢掉锁定位图**。
位图没了 = 那批座位立刻回到可选池 = 同一座位卖出两次。
这不是「慢一点」，是**直接超卖**，而且没有任何报错。

```bash
# 改法(改 redis.conf, 不在运行期用 CONFIG SET 改 —— 重启后失效)
maxmemory-policy noeviction
```

### 1.2 `maxmemory` 必须有上限 —— 阻断

```bash
redis-cli CONFIG GET maxmemory
```

**为什么**：位图是按 offset 分配的，Redis **不回收空洞**。
一个越界的座位索引（历史上出现过 `seat_index=100000`）就能把位图从 18 字节
撑到 12501 字节，同时让 `GET /seat-map` 的响应放大 61 倍。
没有 `maxmemory` 上限，就没有任何刹车。

建议 `512mb` 起（按机器实际内存留 2~3 倍余量）。

### 1.3 位图键上**不能**有 TTL —— 阻断

```bash
redis-cli --scan --pattern 'cinema:session:*:lock' | \
  xargs -I{} redis-cli TTL {}
```

**为什么**：TTL 一到，键自己就没了。演到一半的场次座位凭空释放 → 超卖。

过期回收只允许发生在**已经结束的场次**上（且要由服务端按场次状态主动设置，
不是给所有键一把 TTL）。当前实现没有对位图设 TTL —— 这是刻意的。

### 1.4 `stop-writes-on-bgsave-error` —— 知会项

```bash
redis-cli CONFIG GET stop-writes-on-bgsave-error
```

**为什么**：默认是 `yes`。后台保存失败（磁盘满）时 Redis 会停止接受写入 ——
抢票中途整站卡住，而且错误信息是「命令被拒绝」而不是「磁盘满了」。

改成 `no` + 盯住 RDB 磁盘空间，比留着默认值强。

### 1.5 持久化 —— 知会项

位图丢了能靠 `SeatBitmapGuard.ensureBitmaps` 从 DB 重建（PENDING_PAY / PAID
订单都在库里），所以**不持久化不是致命问题**，只是重启后要冷启动一轮。
开 RDB 快照即可；`appendonly yes` 视部署需要（更安全但更慢）。

### 1.6 Lua 脚本能力 —— 阻断

```bash
redis-cli EVAL "return 1" 0
```

**为什么**：锁座（`lock_seat.lua`）、确认售出（`confirm_seat.lua`）、
退票放位（`refund_seat.lua`）全部是 Lua 脚本。
Lua 被禁 = 这三条路径全废 = 只剩一个「先查再写」的裸实现 = 超卖窗口回来。

## 2. MySQL

| 检查项 | 怎么查 | 不满足会怎样 |
| --- | --- | --- |
| 版本 ≥ 8.0 | `SELECT VERSION();` | `sql/01_schema.sql` 用了 MySQL 8 的语法（生成列 `pending_key`） |
| 字符集 utf8mb4 | `SHOW CREATE DATABASE cinema;` | 影片标题里的 emoji/生僻字写入报错 |
| 时区一致 | `SELECT @@time_zone, @@system_time_zone;` | 场次开始时间与前端 `dayjs` 差 8 小时，选座页出现「已开场」 |
| `sql/03_p0_increment.sql` 已执行 | `SHOW TABLES LIKE 'ticket';` | 电子票域整体缺失（验票接口 500） |
`application-dev.yml` 里的 `serverTimezone=Asia/Shanghai` 要和库时区对得上。

## 3. 后端环境变量

后端读的全部环境变量（`cinema-server/src/main/resources/application.yml`）：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `SPRING_PROFILES_ACTIVE` | `dev` | **生产必须改成 `prod`** —— `dev` 会自动播种 `admin/123456` |
| `JWT_SECRET` | 仓库里的开发密钥 | **生产必须换**，≥32 字节。换之前等于没换：拿到源码就能伪造 `role=1` 的 token |
| `CORS_ALLOWED_ORIGINS` | `http://localhost:5173,http://localhost:4173` | 逗号分隔的白名单。生产填自己的域名，**不要填 `*`** |
| `CINEMA_SEED_ADMIN_ENABLED` | `true` | 生产设 `false`（与 `SPRING_PROFILES_ACTIVE` 双保险） |
| `DEEPSEEK_API_KEY` | 空 | 不设则对话助手返回 `50000`「对话功能未配置」，**其余功能不受影响** |
| `CINEMA_CHAT_ORDER_ENABLED` | `true` | 设 `false` = 关掉助手的一键下单（只读回退闸门，不发版即可生效） |

Windows 上用 `setx` 设 USER 级变量后，**要重开终端**才继承。

```powershell
setx SPRING_PROFILES_ACTIVE prod
setx JWT_SECRET "<32 字节以上的随机串>"
setx CORS_ALLOWED_ORIGINS "https://your-domain.example"
setx CINEMA_SEED_ADMIN_ENABLED false
```

## 4. 前端

### 4.1 开发模式

```powershell
cd cinema-web
pnpm install
pnpm dev        # http://localhost:5173
```

Vite 代理把 `/api` 与 `/ws` 转发到 `http://localhost:8080`。
**必须用 `http://localhost:5173` 访问** —— Vite 只绑 IPv6 `[::1]`，
用 `127.0.0.1:5173` 会连不上（`Test-NetConnection` 也会误报 False）。

### 4.2 预览/部署模式

```powershell
pnpm build
pnpm preview    # http://localhost:4173
```

`preview.proxy` 与 `server.proxy` 同配置（2026-10-24 补齐）。
**早前的版本只配了 `server.proxy`**，于是 preview 模式下 `/api` 与 `/ws`
全都打不到后端 —— 页面空白、WebSocket 连不上，且没有任何错误提示。

### 4.3 生产部署的真实情况

`pnpm build` 产出的是**纯静态文件**，没有后端就没有 `/api`。
正式部署需要自己在前面挂一层反向代理（Nginx / Caddy），把
`/api` 与 `/ws` 转到后端 8080；同时把域名加进 `CORS_ALLOWED_ORIGINS`。

WebSocket 的基址解析规则见 `cinema-web/src/utils/ws.ts` 的 `wsBaseUrl`：
开发端口（5173 / 4173）直连后端 8080，其余情况用当前 host。
**部署时若前端与后端不同源又不同端口，务必配好反向代理的 WS 升级头。**

## 5. 演示数据

```powershell
# 一次性(按顺序)
mysql -uroot -p < sql/01_schema.sql
mysql -uroot -p < sql/02_init_data.sql
mysql -uroot -p < sql/03_p0_increment.sql

# 可选: 更多演示影片与场次
mysql -uroot -p --default-character-set=utf8mb4 < sql/04_extra_demo_data.sql

# 换成真实影片名 + 专属海报(课堂演示用; 必须带 utf8mb4)
mysql -uroot -p --default-character-set=utf8mb4 < sql/07_real_demo_movies.sql

# 刷新演示场次(**每次演示/截图前跑**)
mysql -uroot -p < sql/05_refresh_sessions_for_demo.sql

# 对话助手的 FAQ 知识库(不跑的话助手只能答通则)
mysql -uroot -p < sql/06_qa_knowledge.sql
```

⚠️ **`sql/04_extra_demo_data.sql` 不要重复跑**。它的确定性 ID 用的是
「相对天数偏移」，重跑时算出来的 ID 与上次完全一样，`INSERT IGNORE` 会
**静默跳过每一行** —— 脚本报告成功，实际一行没插。
要刷新场次请用 `sql/05_refresh_sessions_for_demo.sql`（按绝对日期编码 ID，
真正幂等）。

⚠️ `sql/04` 与 `sql/07` 都必须带 `--default-character-set=utf8mb4`，
否则中文片名会被双重编码成乱码。`sql/07` 用的是 `ON DUPLICATE KEY UPDATE`
（可重复执行），`sql/04` 用的是 `INSERT IGNORE`（不可重复执行，见上）。

## 6. 开抢前的最后一分钟

```powershell
# ① Redis 配置
python tools/check_redis_safety.py

# ② 位图与 DB 是否一致
python tools/reconcile_seat_bitmap.py

# ③ 历史脏单
python tools/reconcile_seat_bitmap.py --purge-ghost-orders

# ④ 四个服务的健康度
curl -s localhost:8080/actuator/health
```

`reconcile_seat_bitmap.py` 返回 `1` 表示**有偏差**（不是失败）。
处理方式：

- 泄漏（位图占着，DB 无有效订单）→ `--fix` 清掉。
- 缺失（DB 说该占，位图是空的）→ **危险**，先查 Redis 是否被重启/清空，
  再用管理端「恢复位图」按钮重建。
- 幽灵订单 → `--purge-ghost-orders --fix` 清理。
  已支付的幽灵订单脚本**只报告不自动改**（退款是钱的决策，需人工处理）。

## 7. 已知限制（先知道比撞上强）

| 限制 | 影响 | 现状 |
| --- | --- | --- |
| 位图重建按 DB 订单恢复 | 若在重建瞬间有「已锁座但订单尚未落库」的窗口，重建会丢掉那把锁 | 概率极低（毫秒级），重建只在 Redis 丢数据后触发 |
| `SeatBitmapRebuilder` 不校验座位索引 | 历史脏单若未清理，重建时会把位图重新撑大 | 用 `reconcile_seat_bitmap.py --purge-ghost-orders` 清掉；API 层的越界拦截已修 |
| 单实例部署 | 补偿任务与限流都靠单机内存/Redis，没有多节点协调 | 课程设计范围内可接受 |
| 对话助手依赖外部 LLM | 未配 `DEEPSEEK_API_KEY` 时助手不可用 | 设计如此：其余功能不受影响 |
| 前端无自动化 E2E 回归 | 视图层改动靠人工验收 | 仓库内 vitest 只覆盖纯逻辑与静态契约 |
