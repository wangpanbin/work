# 发布说明 — v0.3.0

- 日期:2026-10-25
- 版本:`cinema-server` 0.2.0 → **0.3.0**;`cinema-web` 0.2.0 → **0.3.0**
- 主题:**收口与修复** —— 文档与代码逐值对齐 · 技术债有明确结论 · 钱与座位交叉路径上不存在已知超卖/漏卖窗口
- 数据库:**无需变更**(不新增表、不改列)

## 一句话

**这一版不加功能,只把已经存在但「文档说的」和「代码做的」对不上的地方逐条对齐,
并修掉三个在钱与座位交叉路径上真实存在的缺陷窗口** —— 其中最严重的一个,
在退票流程中途中断时,会让补偿任务把**别人已经付过款的座位**清成可选。

## 一、修了什么(三个真缺陷)

### 1. 退票释放座位改成「按订单幂等」——堵住一个真实超卖窗口

**之前**:`refund_seat.lua` 无条件清 `sold` + `lock` 两个位。退票主流程是

```
CAS PAID→REFUNDING → 释放座位 → 调渠道退款 → CAS REFUNDING→REFUNDED
```

若在中途中断(进程被杀 / DB 写入异常),订单停在 `REFUNDING`,而**座位已经被释放回可选池**。
补偿任务 5 分钟后再调一次释放通道 —— 此时那批座位若已被他人买走(`sold=1`),
第二次无条件清位会把**别人已付款的座位**清成可选 → 同一座位两张 PAID 订单 = **超卖**。

根因是位图里没有「这张 sold 位属于哪张单」的信息,光看位图判断不了归属。

**现在**:释放动作本身必须按订单幂等。`refund_seat.lua` 新增 `KEYS[3]` 作为
「本单座位已释放过」的标记,**标记与清位在同一次 EVAL 里原子完成**。
补偿任务第二次调用时直接跳过 —— 无论那批座位此刻归谁,都不会再被清一次。

> **有意偏离**:计划原本写「补偿任务改为先 CAS 后释放」。实现保留「先释放 → 再 CAS」——
> CAS 先行会开一个泄漏窗口(CAS 成功后崩溃 → 订单已终结、座位仍占着),
> 而仓库 `OrderMapper.java` 的注释已记录当初就是为避开这个窗口才选的现在这个顺序。
> 幂等标记本身已经完全挡住超卖,不需要动那个顺序。

### 2. 支付 CAS 成功后 Lua 失败 → 座位永久锁死

**之前**:DB 已 CAS 到 `PAID`,但 `confirm_seat.lua` 失败(Redis 抖动)时没有任何补偿 ——
位图里那个座位永远停在 `lock` 态,谁也买不了,系统里也没人会再碰它。

**现在**:`OrderPayService` 失败时调 `SeatBitmapGuard.forceRecover` 从 DB 重建位图。
重建走**原子替换**:位图先建在临时 key 上,建好后再一次性 `RENAME` 覆盖正式 key。
**重建失败时正式位图原封不动** —— 宁可锁死也不误放,只记 error 并提示走管理端「恢复位图」。

> **2026-10-25 code-review 追加修的同类缺陷(超卖级)**:重建原先是「先 `DEL` 正式位图,再 `SETBIT` 建回来」。
> 两次 Redis 调用之间位图是空的,此刻任何一次锁座都会看到「座位可选」→ **已付款的座位被再次卖出**;
> 更糟的是重建本身失败时位图会**永久停在空状态**,整场次座位全部看起来可选。
> 现在改成「临时 key 建好 → 原子换名」,这个窗口没有了。

### 3. 验票的「读-改-写」竞态 → 一票两用

**之前**:`TicketService.verify` 先读出票据、判断未使用、再写 `verified_at`。
两个并发请求可以同时通过判断 → 同一张票被验两次。

**现在**:改成**条件更新**(`WHERE verified_at IS NULL`),让并发下只有一个能改成功。

## 二、技术债修复(都有单测兜底)

| 项 | 问题 | 现在 |
| --- | --- | --- |
| 影厅改行列 | 改完行列后**存量订单的座位索引可能越界**(座位数变少了) | 改行列时若该厅**有过任何订单**就拒绝,并清该厅名下场次缓存 |
| 删除场次 | 删掉有存量订单的场次 → 订单变孤儿 | 删除前校验非终态订单(PENDING_PAY / PAID / REFUNDING),存在则拒绝并列出订单号 |
| 电子票域 | `TicketService` **零测试覆盖** | 新增 `TicketServiceTest`(13 例) |
| `/api/chat/message` | 空消息由 `50000`「系统繁忙」掩盖 | 补 `@Valid` → 返 `40001` 参数错误 |
| 管理端场次列表 | `GET /api/admin/sessions` 一次返回全量(实测 1089 行) | 新增 `GET /api/admin/sessions/page`;**旧端点契约一字未动** |
| 位图重建 | 「先 `DEL` 正式位图,再 `SETBIT` 建回来」在两次 Redis 调用之间留下**空位图窗口** | 改成**临时 key + 原子 `RENAME` 替换**:重建失败时正式位图一个位都不动(宁可锁死也不误放) |

## 三、安全基线

| 项 | 之前 | 现在 |
| --- | --- | --- |
| JWT 密钥 | 写死在 `application.yml` 里,随仓库分发 | `${JWT_SECRET:...}` —— 拿到源码就能伪造 `role=1` 的 token |
| CORS | `allowedOriginPatterns("*")` 全开 | 收敛成 `${CORS_ALLOWED_ORIGINS:...}` 白名单(逗号分隔) |
| 登录 | 无限制流 | 按 **IP + 账号** 10 次/分钟(锁撞库,但不误伤仓库自己的压测脚本) |
| 注册 | 无限制流 | 按 IP 120 次/小时 |
| 管理员播种 | `dev` profile 下强制播种 `admin/123456` | 双开关:`SPRING_PROFILES_ACTIVE` + `CINEMA_SEED_ADMIN_ENABLED`;且不再覆盖已有用户的 role |
| 激活的 profile | 硬编码 `dev`(容器/他人机器都会以 dev 启动) | `${SPRING_PROFILES_ACTIVE:dev}` |

## 四、前端修复

**错误态(以前是「整页空白 + 毫无察觉」)**

- `SeatSelect` 首拉失败 → 页面渲染「加载失败 + 重试」,**而且 WS 照样连上**
  (原先首拉抛异常会中断整个 `onMounted`,`createSeatWs` 根本没被调用 → 实时同步整个会话静默失效)
- `Payment` / `MovieDetail` / `AdminHome` / `LiveDashboard` 同款错误态 + 重试

**接线类问题(逻辑没写错,只是没接上线 —— 这类问题没有任何报错)**

| 问题 | 后果 |
| --- | --- |
| `SeatSelect` 手动刷新按钮直接绑 `refresh` | Vue 把 `MouseEvent` 当成 `preserveSelection=true` 传进去,行为与按钮语义**正好相反** |
| `Payment` 的 3 秒自动跳转定时器从不取消 | 用户在这 3 秒里点「重新选座」,会被定时器**从选座页拽回**订单列表 |
| `OrderList` 写死 `size: 20` 且全仓没有分页组件 | **第 21 条之后的订单永远看不到** |
| `OrderList` 取消/退票后不刷新角标 | tab 上的计数停在旧值 |
| `ChatWidget` 没有 watch 用户 id | 登出再登录,浮窗里还留着**上一个账号**的对话(含订单号/座位号) |
| `MovieDetail` 的 radio-group 与 watch 各触发一次 | 切一个日期发**两次**请求 |
| `AdminHome` 定义了 `logout()` 却没入口 | 管理员无法从后台退出 |
| `Dashboard` 用 `Number(m.revenue)` | 缺失票房算出 `NaN%` |
| `utils/bitmap.ts` 位图短于座位数时缺失位落 0 | 缺失位 = **可选** → 用户能选到一个其实已被占的座位。改为按「占用」处理;base64 非法时抛明确错误而不是让整页崩掉 |
| `ActionCard` 直接渲染 `card.type` | 服务端枚举原样出现在界面上(英文界面里夹英文枚举) |
| 座位 WS 与大屏 WS 各写一套基址策略 | `vite preview` 模式下大屏**永远连不上**且没有任何错误提示。统一为 `wsBaseUrl()` |
| 错误态用了名不副实的 i18n key | 订单加载失败显示「支付失败」、场次加载失败显示「影片加载失败」→ 补 `payment.loadFailed` / `movie.sessionsLoadFailed` |

**顺带清掉两处死代码** —— `ChatWidget` 里只剩注释的空 `onMounted`;`api/admin.ts` 里已无调用方的 `sessionList` 封装

## 八、明确**没做**的事

这一版的定位是收口,不是加功能。以下**一律没做**,并给出结论:

| 项 | 结论 |
| --- | --- |
| 战略计划的 IT-01 / IT-06 / IT-11 / IT-13 | **不做** —— 属于新功能,与本轮目标无关 |
| 位图键加 TTL | **刻意不做** —— TTL 会让演到一半的场次座位凭空释放(超卖)。过期回收只允许发生在**已结束**的场次上 |
| 给 `SeatBitmapRebuilder` 加座位范围校验 | **暂不做** —— API 层的越界拦截已修,历史脏行用 `--purge-ghost-orders` 清掉即可;等真的出现新的越界来源再做 |
| 改本机 `redis.conf` | **不改** —— 只出探针与清单,生产部署前按清单人工执行 |
| 拆分前后端大文件 | **不做** —— 超出本轮范围 |

## 九、升级方式

1. 拉代码。**数据库无需变更**。
2. 建议先跑一遍只读探针:`python tools/check_redis_safety.py`
   —— 返回 `1` 表示有阻断项(比如 `maxmemory-policy` 不是 `noeviction`),
   按 `docs/部署前置检查.md` 逐项处理后再开抢。
3. `mvn spring-boot:run` 启动后端、`pnpm dev` 启动前端。
4. **生产部署**必须设的环境变量(默认值只适合开发):

   ```bash
   export SPRING_PROFILES_ACTIVE=prod
   export JWT_SECRET="<至少 32 字节的随机串>"
   export CORS_ALLOWED_ORIGINS="https://your-domain.example"
   export CINEMA_SEED_ADMIN_ENABLED=false
   ```

   不设 `JWT_SECRET` 就等于没换密钥(仓库里的默认值会兜底);不切 profile 就会
   自动播种 `admin/123456`。
5. 演示前跑 `sql/05_refresh_sessions_for_demo.sql` 补场次(幂等)。
6. 可选体检:`python tools/reconcile_seat_bitmap.py` 与
   `python tools/reconcile_seat_bitmap.py --purge-ghost-orders`。
