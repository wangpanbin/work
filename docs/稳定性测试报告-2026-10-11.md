## 3. 缺陷详情

### P0-1 · `seatIndexes` 缺少范围校验导致 Redis 位图被按 offset 无限膨胀

**等级**: P0(远程内存耗尽 / 公开接口放大)
**位置**:
- `cinema-server/.../modules/order/dto/LockSeatsDTO.java` — 只有 `@NotEmpty` + `@Size(max=4)`, **没有** `@Min(0)`、也没有相对 `seatCount` 的上界
- `cinema-server/src/main/resources/lua/lock_seat.lua:20` — `redis.call('SETBIT', lockKey, tonumber(ARGV[i]), 1)` 无条件按客户端给的 offset 分配
- `cinema-server/.../modules/seat/reader/SessionBitmapReader.java:48-56` — `bytes.length >= expected` 时**原样返回 Redis 里的字符串**(只向上 padding, 从不截断)
- `cinema-server/.../modules/seat/service/SeatService.java:68-69` — 直接 `Base64` 编码该字符串返回

**复现**:

```bash
# 1) 取一个未开场场次的合法座位区间, 例如 session=1130201104, seatCount=140 → 合法索引 0..139
curl -s localhost:8080/api/sessions/1130201104/seat-map | jq '.data.seatCount'   # 140

# 2) 任意登录用户提交一个越界座位索引 (140 就已经越界)
TOKEN=$(curl -s localhost:8080/api/auth/login -H 'Content-Type: application/json' \
        -d '{"username":"user1","password":"123456"}' | jq -r .data.token)
curl -s localhost:8080/api/orders/lock -H "Authorization: Bearer $TOKEN" \
     -H 'Content-Type: application/json' \
     -d '{"sessionId":1130201104,"seatIndexes":[100000]}'
# → {"code":0,"msg":"ok", ...}   越界索引被【接受】

# 3) 量测后果
redis-cli strlen cinema:session:1130201104:lock     # 12501   (正常应为 18 = ceil(140/8))
redis-cli memory usage cinema:session:1130201104:lock  # 25080
curl -s localhost:8080/api/sessions/1130201104/seat-map | wc -c   # 16969  (干净场次 278)
```

**实测量化**(`test/seat_index_bounds_probe.py`, 2026-10-11):

| 提交的 offset | Redis 位图字节数 | 相对正常值(18B) | `GET /seat-map` 响应 | 相对正常值(278B) | Redis 内存占用 |
| --- | --- | --- | --- | --- | --- |
| 100,000 | 12,501 | 694× | 16,969 B | 61× | 25,080 B |
| 1,000,000 | 125,001 | 6,944× | 166,970 B | 601× | 125,083 B |
| 4,000,000 | 500,001 | 27,778× | 666,959 B | **2,399×** | 500,083 B |
| 干净对照 | 18 | 1× | 278 B | 1× | 92 B |

**上界与真实冲击**: Redis `SETBIT` 的硬上界是 `offset = 2^32-1`, 单次即分配
`ceil(2^32)/8 = 536,870,912 字节 = 512 MiB`, 对应 `GET /seat-map` 的 base64 响应约 **683 MiB/次请求**。

本轮实测(见 §3 附注)在本机 Redis 上执行了一次 `SETBIT __probe_bounds__ 4294967295 1`,Redis
`used_memory_peak` 从 803.62K 直接冲到 **641.00 MiB**, 随后 `DEL` 才回落。
`redis-cli SETBIT` 超上界(4294967296)与负 offset(-1)均被 Redis 立即拒绝, 说明**攻击只需卡在 2^32-1 以内**。

**为什么这是"稳定性"问题而不只是"参数校验"问题**:
1. **bitmap 只增不减** —— Redis 的 bitmap 没有缩容操作, 一旦被撑大, 该 key 常驻内存直到过期/删除, 而这里**没有设置 TTL**;
2. **受害接口是公开的** —— `GET /api/sessions/{id}/seat-map` 在 README 中标注为「公开」, 无需登录即可拉取被放大的位图, 放大器效应无门槛;
3. **触发门槛极低** —— `/api/auth/register` 公开, 攻击者自助注册即可拿到 token; `@RateLimit` 为每用户每场次每秒 5 次, 对"换个场次再打一次"毫无约束(本仓库有 1000+ 场次);
4. **单请求即可生效** —— 不需要并发, 一个请求就把内存/带宽放大到 512 MiB 量级。

**影响**: 单实例 Redis 内存耗尽(或触发 `maxmemory` 淘汰, 连带影响锁座正确性) / Tomcat 线程在 base64 编码超大字符串时长时间占用 → 全站不可用。

### P1-1 · 非法座位索引返回 `50000 系统繁忙`, 错误码语义错位

**等级**: P1
**现象**:
```
seatIndexes=[-1]      → {"code":50000,"msg":"系统繁忙,请稍后重试"}
seatIndexes=[-99999]  → {"code":50000,"msg":"系统繁忙,请稍后重试"}
seatIndexes=[null]    → {"code":50000,"msg":"系统繁忙,请稍后重试"}
```
**根因**: 负 offset 会让 Redis 的 `GETBIT` 抛
`ERR bit offset is not an integer or out of range`, 该异常经 `GlobalExceptionHandler` 兜底成 `50000`。
(值得肯定的是: 失败发生在 `lock_seat.lua` 的**第一遍检查循环**里, 尚未执行任何 `SETBIT`, 因此没有留下脏锁位 —— 这一点已实测确认。)

**影响**: 客户端参数错误被计成服务端 5xx 类故障, 会污染监控/告警与错误率统计, 排障时误导定位方向。同一根因(P0-1 的"索引未校验")的另一种表现。

### P2-1 · 列表接口 `page`/`size` 未做边界钳制

**等级**: P2
**实测**(2026-10-11):

| 请求 | 返回 |
| --- | --- |
| `GET /api/movies?page=1&size=5` | `total=20 size=5 records=5` ✅ |
| `GET /api/movies?page=1&size=-1` | `total=0`(**错**) `size=-1` `records=`**20 全量** |
| `GET /api/orders/my?page=1&size=-5` | `total=0`(**错**) `size=-5` `records=`**13 全量** |
| `GET /api/admin/movies?page=1&size=-1` | `total=0`(**错**) `records=`**20 全量** |
| `GET /api/admin/sessions?page=1&size=5` | 直接返回 **1089 行**裸数组, `page/size` 完全未生效 |
| `GET /api/movies?page=1&size=1000000` | `records=`20 全量(`size` 上限未钳制) |

**根因**: MyBatis-Plus 分页在 `size <= 0` 时**关闭分页**并把 `total` 记为 0; 各 Controller 直接透传
`@RequestParam int page/size`, 没有 `@Min(1)`/`@Max(100)` 之类的钳制; `AdminSessionController` 的列表接口干脆没走分页。

**影响**: `size=-1` 可一次性拉全表 —— 目前 `movie` 20 行、`order` 13 行尚可承受, 但 `session` 表已达
**1089 行**(实测 `/api/admin/sessions` 单次响应即 1089 行); 随业务数据增长, 该响应体积线性膨胀, 最终拖慢管理端并形成内存/带宽压力。

### P2-2 · 越界座位索引会落库成"幽灵订单"

**等级**: P2(数据失真)
**证据**(`cinema` 库实查):

```
order_no              session_id    seat_count  total_amount  status  seat_index
2109258624586145794   1130201104    1           45.90         2       140
2109258625794...      1130201104    1           45.90         2       100000
2109252730355900418   1130201201    1           39.90         2       1000000
2109252736169205762   1130101202    1           49.90         2       4000000
```
而 `SELECT MIN(seat_index),MAX(seat_index) FROM seat WHERE hall_id=2` → **0 / 139**。

即: 系统为**根本不存在**的座位生成了合法订单与 `order_item`, 金额照算(45.90 元), 状态机照走,
且 `01_schema.sql` 中**没有任何 `FOREIGN KEY`**(已 grep 确认为空), 数据库层也不会拦截。
座位图上这些位也照置, 但前端按 `seatCount` 渲染网格 → 锁了一个用户永远看不见、也永远点不到的座位。

**影响**: 订单/营收统计被污染(§admin dashboard 营收会把幽灵订单计入), 且用户可能为不存在的座位付款。

## 5. 修复实施(本轮已落代码)

### 5.1 P0-1 / P1-1 / P2-2 —— 座位索引范围校验(写入侧根因)

**改动 1: `OrderCore#requireSeatsInRange`(新增, 权威校验点)**

上界取决于场次(1 号厅 96 座 / 2 号厅 140 座), 无法用常量注解表达, 因此放在服务层,
seatCount 取 `SessionInfoLoader`(与 `GET /seat-map` 同一来源, 保证"客户端看得到的座位"
与"服务端允许锁的座位"完全一致):

```java
public void requireSeatsInRange(Long sessionId, List<Integer> seats) {
    int seatCount = sessionInfoLoader.load(sessionId).getSeatCount();
    if (seatCount <= 0) {
        throw new BizException(ResultCode.BAD_REQUEST.getCode(),
                "场次座位数异常, 无法锁座(sessionId=" + sessionId + ", seatCount=" + seatCount + ")", null);
    }
    for (Integer idx : seats) {
        if (idx == null || idx < 0 || idx >= seatCount) {
            throw new BizException(ResultCode.BAD_REQUEST.getCode(),
                    "座位索引越界: " + idx + ", 本场次有效范围 [0, " + (seatCount - 1) + "]", null);
        }
    }
}
```

放在 `OrderCore` 而不是 `OrderLockService` 的原因: `OrderCore` 已经是"订单公共校验"的归属地
(它已有 `requirePurchasableSession` / `requirePending`), 而且 `OrderLockServiceTest` 里
`OrderCore` 是 mock, 加在这里不会破坏既有 5 个用例的构造签名。

**改动 2: `OrderLockService#lockSeats` 调用守卫 + 过滤 null**

```java
List<Integer> seats = dto.getSeatIndexes().stream()
        .filter(java.util.Objects::nonNull)   // 防 stream.sorted() 对 null 抛 NPE
        .distinct().sorted().toList();
if (seats.isEmpty() || seats.size() > 4) { throw new BizException("每次最多选择4个座位"); }

Session session = orderCore.requirePurchasableSession(sessionId);
orderCore.requireSeatsInRange(sessionId, seats);   // ← 新增, 在进 Lua 之前拦掉
seatBitmapGuard.ensureBitmaps(sessionId);
```

注意校验位置**必须在 `seatLuaService.lockSeats(...)` 之前** —— 一旦进了 Lua 的 `SETBIT`,
Redis 的内存分配就已经发生且不可回收。

**改动 3: `LockSeatsDTO` 元素级约束(DTO 层快速失败)**

```java
@NotEmpty(message = "请至少选择一个座位")
@Size(max = 4, message = "每次最多选择4个座位")
private List<@NotNull(message = "座位索引不能为空")
             @Min(value = 0, message = "座位索引不能为负数")
             @Max(value = 4095, message = "座位索引超出影厅最大座位数") Integer> seatIndexes;
```

`@Max(4095)` 只是远高于任何影厅的兜底 —— **它挡不住"96 座厅传 139"**, 真实上界由改动 1 负责。

**改动 4: `SessionBitmapReader#readWithPadding` 读侧截断(抵御历史脏位图)**

```java
if (bytes.length > expected) {
    return java.util.Arrays.copyOf(bytes, expected);   // 只向上 padding → 同时向下截断
}
return bytes;
```

bitmap 没有缩容操作, 已被撑大的 key 不会自己变小; 这一刀保证**响应体积只由 seatCount 决定**,
与 Redis 内部残留无关, 也给"修复上线前已被污染的场次"止血。

> **未采纳**: `lock_seat.lua` 里加 maxSeat 断言。该方案要改 ARGV 协议(所有调用方 + SHA 全变),
> 收益是"防未来绕过 Service 的调用方"; 当前 `lockSeats` 是唯一入口, 先用 Service 层守住,
> 避免为一次修复改动被多组测试锁定的 Lua 契约。

### 5.2 P2-1 —— 分页入参钳制

新增 `com.cinema.common.web.PageParams`, 在 3 个分页接口统一钳制:

```java
public static final int MAX_SIZE = 100;          // 前端实际用到 size=100(SessionManage.vue)
public static int page(int page) { return Math.max(1, page); }
public static int size(int size) { return Math.min(Math.max(1, size), MAX_SIZE); }
```

应用点: `MovieController#search`、`AdminMovieController#page`、`OrderController#my`。
`MAX_SIZE=100` 的取值依据是"前端已知最大 size 就是 100", 不截断任何现有页面。

> **未改**: `/api/admin/sessions`(`R<List<Session>>` 裸列表, 一次返回 1089 行)。
> 把它改成分页会破坏 `SessionManage.vue` 的返回类型契约, 属于前后端联动改动,
> 建议单独开 issue 评估。本轮只在 §0 表格里记为 P2-1b。

> **仍建议(未做)**: 给两个位图 key 补 `EXPIRE`, 并给 Redis 配 `maxmemory` +
> `maxmemory-policy noeviction`(避免内存打满时把锁座数据淘汰掉反而造成超卖)。
