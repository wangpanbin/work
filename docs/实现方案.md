## 4. 数据模型

### 4.1 MySQL 表（8 张）

```
cinema       影院：id, name, address
hall         影厅：id, cinema_id, name, rows, cols, seat_count
seat         座位：id, hall_id, seat_index(0~N-1，对应 bitmap 位),
                  row_no, col_no, seat_type(0普通/1VIP), x, y
                  UNIQUE KEY uk_hall_seat (hall_id, seat_index)
movie        影片：id, title, poster, duration, description, status(0下架/1热映)
session      场次：id, movie_id, hall_id, start_time, end_time, price, status(0待开售/1在售/2已开场/3已结束)
user         用户：id, username(UK), password(BCrypt), nickname, phone, created_at
order        订单：见 4.2
order_item   订单座位：id, order_id, session_id, seat_index, price
                  UNIQUE KEY uk_order_seat (order_id, seat_index)
                  KEY idx_session_seat (session_id, seat_index)
```

> 保留字处理：`order` / `user` / `session` 在 DDL 中用反引号，实体上 `@TableName("`order`")` 等。

### 4.2 订单表与防重核心

```sql
CREATE TABLE `order` (
  id            BIGINT       PRIMARY KEY,            -- 雪花 ID
  order_no      VARCHAR(32)  NOT NULL,               -- 雪花生成的业务单号
  user_id       BIGINT       NOT NULL,
  session_id    BIGINT       NOT NULL,
  status        TINYINT      NOT NULL DEFAULT 0 COMMENT '0待支付 1已支付 2已取消',
  total_amount  DECIMAL(10,2) NOT NULL,
  seat_count    INT          NOT NULL,
  expire_at     DATETIME     NOT NULL COMMENT '支付截止时间',
  paid_at       DATETIME     NULL,
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  -- ★ 生成列：仅待支付订单参与唯一约束（MySQL 不支持部分索引的替代方案）
  pending_key   BIGINT GENERATED ALWAYS AS (CASE WHEN `status` = 0 THEN session_id END) STORED,
  UNIQUE KEY uk_order_no (order_no),
  UNIQUE KEY uk_user_pending (user_id, pending_key),   -- 同用户同场次仅一张待支付单
  KEY idx_status_expire (status, expire_at),           -- 兜底补偿扫描
  KEY idx_user (user_id, created_at)
);
```

订单状态机：`0 PENDING_PAY → 1 PAID`（支付成功）或 `0 PENDING_PAY → 2 CANCELLED`（超时/主动取消）。终态不可逆，所有状态迁移必须 **CAS**（`UPDATE ... WHERE status=0`），见 §6。

### 4.3 Redis Key 设计

| Key | 类型 | 用途 | TTL |
| --- | --- | --- | --- |
| `cinema:session:{sid}:lock` | Bitmap | 已锁定（含已售）座位位图 | 到场次结束 |
| `cinema:session:{sid}:sold` | Bitmap | 已售出（已支付）座位位图 | 到场次结束 |
| `cinema:session:{sid}:lock:rebuild` | Bitmap | 位图**原子替换**的临时 key：先建在这里, 建好后再 `RENAME` 覆盖正式 key | 用完即随换名消失 |
| `cinema:session:{sid}:sold:rebuild` | Bitmap | 同上（sold 位图） | 用完即随换名消失 |
| `cinema:session:info:{sid}` | Hash | 场次信息缓存（影片/影厅/时间/价格） | 到场次结束 |
| `cinema:hall:layout:{hid}` | String | 影厅座位布局 JSON（行/列/坐标/类型） | 1h + 管理端变更时失效 |
| `cinema:user:pending:{uid}:{sid}` | String | 用户在本场次的待支付订单号（**只写镜像**，查询一律以 DB 为准） | 15min（=锁座时长） |
| `cinema:user:locked:{uid}:{sid}` | Hash | 用户在本场次锁定的座位（field=seatIndex, value=orderNo） | 15min |
| `cinema:order:timeout` | ZSet | **延迟关单队列**，member=orderNo，score=expireAt 毫秒 | — |
| `cinema:seat:event:seq` | String | 座位事件全局单调序号（`INCR`，**不设 TTL**） | — |
| `cinema:order:seat-released:{orderNo}` | String | **退票释放的按订单幂等标记**（防补偿任务二次清掉他人已付款座位） | 24h |
| `cinema:chat:proposal:{id}` | String | 对话助手下单提案快照（**不占位**，一次性） | 90s |
| `seat:event`（channel） | Pub/Sub | 座位变更事件广播（跨实例就绪） | — |

> 修正 plan.md：待支付订单 key 由 `cinema:user:pending:{uid}` 改为 **`{uid}:{sid}`** —— 用户可同时持有多个场次的待支付订单（每场次限一单），带 sid 才不互相覆盖。

**座位状态推导**（前端渲染依据）：

| lock 位 | sold 位 | 含义 |
| --- | --- | --- |
| 0 | 0 | ✅ 可选 |
| 1 | 0 | 🔒 已锁（他人待支付） |
| 1 | 1 | ⬛ 已售 |
| 我锁的 | | 从 `cinema:user:pending:{uid}:{sid}` 判断，无需 owner 结构 |

**Bitmap 长度分配在读侧惰性完成**：`SeatService.seatMap` 走 `SessionBitmapReader.readWithPadding(key, seatCount)`，首次读到某个场次的位图时才把长度补到位。**新建场次不需要预热** —— 没有 Redis key 的场次直接返回全 0（全部可选）的座位图。

> ⚠️ 位图字符串**不会因为清零高位而收缩**：Redis 按 offset 分配空间，`SETBIT key 100000 0` 之后 `STRLEN` 仍是 12501。位图体积只降不升，所以越界座位索引必须在上线前拦住（见 §6.1 的范围校验）；已经撑大的位图用 `tools/reconcile_seat_bitmap.py --purge-ghost-orders --fix` 重建（DEL + 按合法位重写，原子）。

**为什么 Bitmap 而不是 Set**（报告要点）：300 座 ≈ 38 字节 vs Set 数 KB；`SETBIT/GETBIT` O(1) 原子；`GETRANGE` 一次取回全图；单 Key 位操作单节点 10w+ QPS，课程设计**不分段**（避免 Lua 多 Key/Cluster hash tag 复杂化），这是有意为之的"不过度设计"权衡。

### 4.4 Lua 脚本（`resources/lua/`，DefaultRedisScript 预加载为 Bean）

**① lock_seat.lua — 锁座（防超卖核心）**

```lua
-- KEYS[1]=lock bitmap, KEYS[2]=sold bitmap; ARGV[1..]=座位索引
local lockKey, soldKey = KEYS[1], KEYS[2]
local conflict = {}
for i = 1, #ARGV do
    local seat = tonumber(ARGV[i])
    if redis.call('GETBIT', soldKey, seat) == 1
       or redis.call('GETBIT', lockKey, seat) == 1 then
        table.insert(conflict, seat)
    end
end
if #conflict > 0 then
    return cjson.encode({ok = false, conflict = conflict})
end
for i = 1, #ARGV do
    redis.call('SETBIT', lockKey, tonumber(ARGV[i]), 1)
end
return cjson.encode({ok = true, conflict = {}})
```

**② confirm_seat.lua — 支付确认（lock → sold）**

```lua
-- KEYS[1]=lock, KEYS[2]=sold; ARGV=座位索引
local confirmed = {}
for i = 1, #ARGV do
    local seat = tonumber(ARGV[i])
    if redis.call('GETBIT', KEYS[1], seat) == 1 then
        redis.call('SETBIT', KEYS[2], seat, 1)
        table.insert(confirmed, seat)
    end
end
return cjson.encode(confirmed)
```

**③ release_seat.lua — 超时/取消释放（只清未售的）**

```lua
-- KEYS[1]=lock, KEYS[2]=sold; ARGV=座位索引
local released = {}
for i = 1, #ARGV do
    local seat = tonumber(ARGV[i])
    if redis.call('GETBIT', KEYS[2], seat) == 0 then
        redis.call('SETBIT', KEYS[1], seat, 0)
        table.insert(released, seat)
    end
end
return cjson.encode(released)
```

**④ refund_seat.lua — 退票释放（同时清 sold + lock）**

```lua
-- KEYS[1]=lock, KEYS[2]=sold, KEYS[3]=按订单幂等标记; ARGV[1]=标记 TTL 秒, ARGV[2..]=座位索引
-- KEYS[3] 已存在 → 本单座位已释放过, 直接返回空列表, 不再碰任何位
```

> release / confirm / refund 三者语义**不可混用**：`release_seat` 只清未售的锁定位（待支付单超时/取消用），`confirm_seat` 置 sold 并同步清 lock，**`refund_seat` 同时清 sold + lock**（退票专用）。退票误用 `release_seat` 会导致座位 sold 残留、永久不可再售。

> **幂等标记为什么必要**（2026-10-24，防超卖）：退票主流程是「CAS PAID→REFUNDING → 释放座位 → 调渠道退款 → CAS REFUNDING→REFUNDED」。若中途中断，订单停在 REFUNDING 而座位已回到可选池；补偿任务 5 分钟后再调一次释放，若那批座位已被他人买走，第二次无条件清位会把**别人已付款的座位**清成可选 → 同一座位两张 PAID 订单 = 超卖。位图里没有「这张 sold 位属于哪张单」的信息，所以释放动作必须按订单幂等：标记与清位在同一个 Lua 里原子完成。

> confirm/release 的位判断是**双花防护的 Redis 侧**：release 只清未售位，confirm 只把仍处于 lock 的位置为 sold —— 即使支付与超时关单并发，两个脚本的执行顺序无论谁先，结果都是一致的（要么 sold，要么回到可选，不会既售又释放）。

**⑤ replace_seat_bitmap.lua — 位图原子替换（重建用，2026-10-25）**

```lua
-- KEYS[1]=临时 lock, KEYS[2]=临时 sold, KEYS[3]=正式 lock, KEYS[4]=正式 sold
-- ARGV[1..]=N, lock 座位索引..., M, sold 座位索引...
-- 先在临时 key 上建好位图, 再一次性 RENAME 覆盖正式 key
```

> **为什么不能「先删后建」**：`SeatBitmapGuard.forceRecover` 与冷启动重建原先是「先 `DEL` 正式位图，再 `SETBIT` 建回来」。两次 Redis 调用之间正式位图是空的，此刻任何一次锁座都会看到「座位可选」→ **已付款的座位被再次卖出（超卖）**；重建本身失败时位图还会**永久停在空状态**，整场次座位全部看起来可选。
>
> 改成「临时 key 建好 → 原子换名」后：换名之前正式位图原封不动（重建失败 = 座位保持已锁/已售，宁可锁死也不误放）；两次换名在同一个 Lua 脚本里完成，脚本执行期间不会有其他客户端的命令插进来，不存在「换了一半」的中间态。
>
> 旧的 `recover_seat_bitmap.lua`（合并语义的 `SETBIT`）已删除 —— 它**有**生产调用方（`SeatBitmapGuard.ensureBitmaps` → `OrderLockService.lockSeats`），删除的原因是它「先 `DEL` 再建」的那道空窗。
>
> **v0.4.0 二次评审再修一处：重建改成「合并」而不是「替换」。**
>
> 「临时 key + 原子 RENAME」只挡住了**失败**那道口（重建失败 = 正式位图原封不动），却漏了**并发**那道口：DB 快照是在脚本之外查的（`SeatBitmapRebuilder` 查库 → 拼快照 → 才进脚本），两者之间隔着一次网络往返。那段时间里任何一次锁座都会把位写进正式位图，而这份锁**不在快照里**（订单行可能还没提交）→ RENAME 覆盖后被抹掉 → 座位回落为「可选」→ 另一人可以锁到同一座位 → 同一座位两张待支付单 = **超卖**。
>
> 冷启动路径（`ensureBitmaps`）尤其危险：位图刚被清掉，所有人同时抢座，窗口内的每一把锁都会被抹掉。
>
> 现在是 `merge_seat_bitmap.lua`：**合并结果 = 正式位图 OR DB 快照**（只加不减），且合并与换名在同一个脚本里原子完成 —— 脚本执行期间不会有别的命令插进来，「快照之后新产生的锁」一定已经落在正式位图里，OR 之后被完整保留。
>
> 语义变化：**座位只可能变不可选，绝不可能变可选**（宁可锁死也不误放）。代价是位图**不再自动收缩** —— 高位泄漏位与体积收缩交给离线工具`tools/reconcile_seat_bitmap.py --fix`（显式带 `--fix` 开关的运维动作）。

## 5. 延迟关单：Redis ZSet 方案（替代 RabbitMQ）

**接口抽象**（`infra/delay/`）：

```java
public interface DelayQueue {
    void offer(String message, long delayMillis);          // 投递延迟消息
    List<String> pollExpired(int batch);                    // 取出到期消息
    default String name() { return "redis-zset"; }
}
```

**RedisDelayQueue 实现**：`ZADD cinema:order:timeout <expireAtMillis> <orderNo>`；`pollExpired` 用 `ZREMRANGEBYSCORE` 原子弹出 `score <= now` 的成员（先 remove 后处理，处理失败重新入队——关单逻辑本身幂等，见下）。

**OrderTimeoutScanner**（`@Scheduled(fixedDelay = 5000)`）：每 5 秒 `pollExpired` → 逐个执行 `closeIfUnpaid(orderNo)`。

**OrderTimeoutCompensateJob**（`@Scheduled(fixedDelay = 60000)`）：每分钟扫 `status=0 AND expire_at < now` 的订单补执行关单 —— 防 ZSet 消息丢失/被误删，双保险。

**closeIfUnpaid 幂等流程**：

```
1. CAS：UPDATE `order` SET status=2 WHERE order_no=? AND status=0
2. affected == 1 才继续（支付成功/已取消的订单自然跳过）
3. release_seat.lua 释放座位位图
4. DEL cinema:user:pending:{uid}:{sid}
5. 广播 SeatEvent.RELEASED
```

**与 RabbitMQ 方案权衡**（报告要点）：
- ZSet 方案：零新增依赖、实现 30 行、精确到秒级；代价是需要自己兜底（本方案已含定时补偿）、消息无 ACK 机制（靠幂等弥补）。
- RabbitMQ TTL+死信：可靠性语义更完整；代价是 Windows 安装 Erlang+MQ 重、延迟插件需额外安装。
- 代码保持 `DelayQueue` 接口，后续可加 `RabbitMqDelayQueue` 实现按配置切换，业务层零改动。

## 6. 核心业务流程（代码级时序）

### 6.1 锁座下单（W2 实现）

```
POST /api/orders/lock {sessionId, seatIndexes[]}
1. 校验：1≤座位数≤4；场次 status=1 在售；start_time > now；座位索引合法且连续可选（可选校验）
2. 幂等防重：若存在同场次待支付单（先查 cinema:user:pending:{uid}:{sid}，再查 DB 兜底）
   → 先执行其超时释放流程（release + 取消旧单），再继续新锁座
3. ★ Redis Lua 原子锁座 lock_seat.lua —— 失败返回冲突座位列表给前端刷新
4. 落库：INSERT `order`(PENDING_PAY, expire_at=now+15min) + 批量 INSERT order_item
   （uk_user_pending 兜底并发重复下单：捕获 DuplicateKeyException → 释放刚锁的座位，返回业务错误）
5. ZSet 入队 + SET cinema:user:pending:{uid}:{sid} orderNo EX 900
6. 广播 SeatEvent.LOCKED（Redis Pub/Sub → WS 推给本场所有连接）
7. try/catch：第 4 步之后任何异常 → 补偿 release_seat.lua，防"幽灵锁座"
```

### 6.2 模拟支付（W3）

```
POST /api/orders/{orderNo}/pay
1. 查单校验：属于本人 + status=0 + expire_at > now
2. 模拟支付渠道成功（1~2s 延迟模拟）
3. ★ CAS：UPDATE `order` SET status=1, paid_at=now WHERE order_no=? AND status=0
   affected==0 → 说明已被超时关单，抛"订单已超时，座位已释放"
4. confirm_seat.lua：lock → sold
   （v0.3.0：Lua 失败会触发 `SeatBitmapGuard.forceRecover` 从 DB 重建位图；
    重建走「临时 key + 原子 RENAME」替换，重建失败时**正式位图一个位都不动**
    —— 宁可锁死也不误放，位图宁死不能放出超卖）
5. 广播 SeatEvent.SOLD；清除 pending key
```

### 6.3 超时释放

见 §5。**支付 vs 关单竞态**由两层防护保证：
- DB CAS 只有一方能把 status 从 0 迁走；
- Lua 脚本位判断保证 Redis 位图最终一致（§4.4）。

### 6.4 WebSocket 实时同步（W3）

- 端点 `ws://localhost:8080/ws/seat/{sessionId}?token=<JWT>`，握手拦截器校验 token。
- `SeatWsHandler`：`Map<Long, Set<WebSocketSession>> roomMap` 管理本场连接。
- `SeatEventPublisher`：业务侧 `convertAndSend("seat:event", json)` → `SeatRedisSubscriber` 收到后推给本机 roomMap 对应场次的所有连接（单实例也走 Pub/Sub，多实例天然就绪）。
- 事件格式：`{"type":"LOCKED|RELEASED|SOLD","sessionId":1001,"seats":[12,13]}`

### 6.5 幂等/一致性防护矩阵

| 风险 | 防护 |
| --- | --- |
| 超卖 | lock_seat.lua 原子检查+锁定（单线程 Lua） |
| 同用户同场次重复占座 | uk_user_pending 生成列唯一索引 + pending key |
| 重复支付 | 支付 CAS status 0→1 |
| 支付与超时竞态 | 双方均 CAS + Lua 位判断 |
| DB 失败幽灵锁 | 落库 try/catch 补偿释放 |
| MQ/ZSet 丢消息 | 每分钟 DB 兜底扫描补偿 |

## 8. 关键设计权衡（答辩要点）

1. **JWT + Interceptor 而非 Spring Security**：课程设计只需登录态与角色，Security 过滤链配置成本高收益低；Interceptor + ThreadLocal（UserContext）足够，且链路更直观。
2. **不用 Redisson**：防超卖靠 Lua 原子性、防重复占座靠 DB 唯一索引、防重复支付靠 CAS —— 三个风险点都有更精准的手段，分布式锁反而是大锤敲钉子；仅在 W4 若出现"管理端改场次与用户下单并发"场景再按需引入。
3. **单体优先**：先单实例 + Redis，能压测能演示；WS 已通过 Redis Pub/Sub 为多实例就绪，应用本身无状态可 `--scale`。
4. **Redis ZSet vs RabbitMQ**：见 §5。
5. **生成列唯一索引 vs 业务层查后插**：查后插有并发窗口；生成列把"待支付唯一"下推到存储层，兜底一切并发路径。

## 9. 前端设计要点（W2~W4）

- `SeatMap` 组件：CSS Grid 按 row_no/col_no 布局；`utils/bitmap.ts` 将 base64 位图解码为 `Uint8Array`；状态机 `AVAILABLE|SOLD|LOCKED_OTHER|LOCKED_MINE|SELECTED`（见 plan.md §4.2，`myLocked` 从 seat-map 接口的 `myLockedSeats` 构建）。
- `utils/ws.ts`：重连（3s 起指数退避）+ 心跳；`onmessage` 局部更新 Pinia seat store，不整页刷新。
- 锁座返回冲突 → ElMessage「座位已被抢走」+ 自动重拉座位图。
- 倒计时：dayjs 计算 expireAt 差值，到 0 触发关单态。
- 300 座 v-for 渲染无压力；>1000 座再考虑 Canvas（文档提一句即可）。
